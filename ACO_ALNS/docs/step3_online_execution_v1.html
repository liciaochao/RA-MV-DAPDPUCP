4.1 Online Execution Stage Overview

First, the online stage is positioned as the execution layer that receives an already optimized offline structural solution, where the offline layer provides the truck route sequence, sortie list, pair assignment state, and expected-cost calibration coefficients, while the online layer receives this structure as planned_solution and executes it under realized customer absence. Subsequently, the online stage no longer optimizes under expectation over all unobserved events; instead, it runs a realized trajectory under sampled binary presence and updates the remaining plan only when a not-home event is observed. Finally, the essential distinction is therefore deterministic expectation optimization offline versus stochastic realized response online.

Subsequently, the main challenge is that customer absence uncertainty enters execution as node-level event revelation, because binary outcomes in home_status are sampled from home_probabilities and then consumed by the event engine. In turn, irrevocability appears because visited truck nodes, started sorties, and sortie prefixes before a failed customer are frozen through frozen_customers, which constrains the feasible neighborhood for replanning. As a result, real-time response must compress search depth, since only a lightweight online ALNS with strict-improvement acceptance and a short fixed iteration budget is allowed during execution.

Consequently, the global logic is an execution-sensing-decision loop over each pair route: the engine advances arc by arc, checks truck-side and drone-side not-home events at reached nodes, dispatches event objects, repairs affected sorties, freezes executed decisions, and performs local remaining-path optimization on the affected pair. Once each repair has been completed, timeline and load states are recomputed so that subsequent sortie feasibility is validated before continuing traversal. Thereafter, actual cost is accumulated from realized truck distance, realized drone energy, and realized failure penalties.

Finally, this chapter is organized so that Section 4.2 formalizes online initialization from offline outputs, Section 4.3 details the execution loop and node-level service actions, Section 4.4 explains failure processing and local replanning decisions, Section 4.5 clarifies online feasibility-preservation mechanisms, Section 4.6 summarizes realized-cost reporting structures, Section 4.7 discusses budget-complexity implications of online optimization compression, and Section 4.8 provides a consolidated implementation-level interpretation of the complete online stage.

4.2 Online Initialization from Offline Solution

Step 1: Reception of offline solution and initialization of execution state.

This step is performed because the online engine cannot execute events without an initial structural carrier that already specifies which pair visits which nodes and which customers belong to each sortie. Once planned_solution has been passed into ExecutionEngine.run, the engine deep-copies it into current_solution so that online mutations do not corrupt the offline baseline, and this copied state becomes the mutable execution plan.

Subsequently, initialization of dynamic execution variables is completed by constructing the realized home-status map, by preparing per-trial distance and energy accumulators, and by preparing snapshot containers for replanning history. In turn, the first executable state is therefore the tuple containing the copied solution, realized home-status map, and zeroed realized-cost accumulators.

\tag{76}
\end{equation}

In Eq. 4.3 Online Execution Main Loop

4.3.1 Main-loop structure overview

The implemented loop is primarily node-arrival-driven over each pair route index rather than globally time-stepped. First, the engine advances from one truck arc to the next, records traveled distance, and then performs node-local event checks. Subsequently, if a not-home event is detected, event dispatch is immediately executed and the current solution is replaced by the returned replanned solution before the loop continues; as a result, loop progression and decision updates are tightly interleaved.

Loop termination occurs when the route cursor reaches the last node of the current pair route, after which the engine moves to the next pair identifier. Once all pair routes have been completed, timelines are recomputed for realized reporting, realized costs are aggregated, and execution output is returned. Consequently, the stopping condition is structural exhaustion of all route positions, and the loop-internal decision sequence is travel update, truck-event check, drone-event scan at launch node, optional replanning, and continuation.

4.3.2 Node arrival and service attempts

Step 1: Truck arrival at current node.

This step is performed because every subsequent service and sortie decision depends on realized node arrival times propagated from previous departures. Once the truck moves from prev to curr, arrival is computed by adding travel time to the previous departure, and if the node is a recovery node the truck availability is synchronized with drone arrival before service-start evaluation.

Subsequently, node role is inferred by membership in truck customers, sortie launch anchors, sortie recovery anchors, or depot identity, and this role determines whether service, launch, recovery merge, or direct pass-through behavior applies. In turn, time-window comparison is executed online at customer nodes through earliest-start and latest-bound logic embedded in timeline and feasibility routines. 

\begin{equation}
AT_T(v_k)=DT_T(v_{k-1})+\frac{d_T(v_{k-1},v_k)}{v_T},
\qquad
A^{\mathrm{avail}}_k=\max\{AT_T(v_k),AT_D(v_k)\}\;\text{if }v_k\in\mathcal{R}.
\tag{81}
\end{equation}

\begin{equation}
ST_T(v_k)=\max\{A^{\mathrm{avail}}_k,e_{v_k}\},
\qquad
DT_T(v_k)=ST_T(v_k)+\hat{h}_{v_k}\,s_{v_k}.
\tag{82}
\end{equation}

In Eq. (81), AT_T corresponds to timeline.truck_arrival, DT_T corresponds to timeline.truck_departure, d_T uses instance.truck_distance_km and instance.truck_travel_time, and \mathcal{R} denotes recovery nodes detected via find_sortie_by_recovery. In Eq. (82), ST_T is service start, e_i is customer.time_window[0], and s_i is customer.service_time.

Satisfaction is declared when timeline propagation yields finite arrivals and departures consistent with route order. A violation occurs when required predecessor departures or synchronized drone arrivals are missing; in that case, timeline computation raises errors and the caller handles the exception by skipping the inconsistent replanning branch.

The output of this step is a realized arrival-departure state at the current node that is ready for event detection and service decisions.

Step 2: Customer home-status revelation at execution time.

This step is performed because service feasibility in online execution depends on realized rather than planned presence. Once the loop reaches a truck-customer node, absence is checked directly from home_status; once a sortie launched at the current node is scanned, each remaining absent customer is detected through the same map and converted into a drone event.

Subsequently, revelation affects all downstream timing and load updates because not-home customers consume no service time and do not update payload transfers that require successful service. As a result, revelation at one customer can shift the departure and recovery timeline for the same sortie and may cascade to later launch windows through recomputation. 

\begin{equation}
\text{Reveal}(i,k)=\hat{h}_i
\quad\text{when node/scan position }k\text{ reaches service attempt for }i.
\tag{83}
\end{equation}

In Eq. (83), revelation is operationalized by direct access to home_status[i] in execution checks. Truck-side revelation occurs at route node reach, while drone-side revelation occurs during launched-sortie customer scan.

Satisfaction is declared when each service attempt uses the current binary map without overwriting unrelated customers. A violation occurs when stale sortie indices or inconsistent pair membership prevent proper location of the event customer; in that case, the replanner returns without mutation for that event path.

The output of this step is an event-ready local truth state that directly conditions immediate service and replanning actions.

Step 3: Service-attempt decision and outcome classification.

This step is performed because execution must separate realized success from realized failure before deciding whether to continue traversal or trigger replanning. Once a truck node is reached, success corresponds to customer membership plus presence truth, whereas failure corresponds to membership plus absence truth; similarly, drone-side failure corresponds to absent customers inside launched sorties that have not yet been handled in the current scan.

Subsequently, a successful attempt keeps the loop on the current plan without event dispatch, whereas a failed attempt immediately instantiates CustomerNotHomeEvent and routes control to the replanner. In turn, this event-first architecture means that failure processing is explicit and success remains the implicit continuation branch. 

\begin{equation}

\tag{84}
\end{equation}

\begin{equation}
C^{\mathrm{fail}}_{\mathrm{real}}=\sum_{i\in\mathcal{F}}Z_{\mathrm{fail}}(i),
\qquad
Z_{\mathrm{fail}}(i)=2\,d_T(0,i)\,c_T.
\tag{85}
\end{equation}

In Eq. (84), \mathcal{C}^{mode} is either pair_solution.truck_customers or the launched-sortie customer list under scan. In Eq. (85), \mathcal{F} is the realized failed-customer set failed_customers, and Z_fail(i) uses failure_penalty(instance, i, params).

Satisfaction is declared when each failed customer generates exactly one actionable event in the current scan context. A violation occurs when the same absent customer would be repeatedly processed; in that case, local handled_customers guards prevent duplicate processing in one launch-scan loop.

The output of this step is a binary event decision that either continues execution or invokes online replanning.

This step is performed because launch-recovery coupling must be explicitly synchronized with truck progression, and failure within a sortie can invalidate only a suffix rather than the entire pair route. Once launch is reached, drone timeline is instantiated from truck departure at launch, customers are traversed in sortie order, and recovery arrival is synchronized against truck arrival for waiting feasibility.

Subsequently, if an in-sortie customer fails, the replanner repairs the current sortie by skip, truncate, and reorder logic, then recomputes timeline and load states and validates downstream sorties. As a result, the sortie process is treated as a dynamically repairable sequence constrained by battery, payload, synchronization, and frozen-prefix rules.

This step is performed because realized performance must be measured on the executed trajectory rather than on offline expectation terms. Once execution loops complete, the engine aggregates fixed pair cost, realized truck distance cost, realized drone energy cost, and realized failure penalties, and the result is stored in the execution output object.

4.4 Service-Failure Handling and Online Replanning

4.4.1 Failure classes and detection logic

Online execution includes heterogeneous failures with different operational scopes. Truck-side not-home failures are node-local events that directly affect the current truck customer and the future suffix. Drone-side not-home failures occur inside a launched sortie and therefore trigger sortie-local repair before remaining-path optimization. Time-window-related feasibility failures are not directly emitted as standalone events in execution traversal; instead, they appear through feasibility checks during repair or candidate acceptance, where they can reject candidate updates or force sortie repair. Consequently, response pathways are mode-dependent even though all pathways eventually update the same solution object.

Failure Type 1: Truck-served customer not at home.

This operation is performed because truck-arrival service failure is the earliest observable disruption on the truck backbone and must be converted into an actionable replanning signal. Once the route cursor reaches a node that belongs to truck_customers and the realized home-status entry is false, the engine builds a truck-mode CustomerNotHomeEvent and dispatches it.

Subsequently, the truck-event handler updates absence truth for that customer, repairs any now-infeasible sorties, freezes already traversed decisions, and runs lightweight remaining-path optimization on the same pair. As a result, response is immediate and local to the affected pair without restarting offline global search. 

\begin{equation}
\mathbb{I}^{\mathrm{truck\_event}}_i
=\mathbb{I}\{i\in\mathcal{C}^{T}\}\cdot(1-\hat{h}_i).
\tag{89}
\end{equation}

In Eq. (89), \mathcal{C}^T is pair_solution.truck_customers and \hat{h}_i is home_status[i]. Event creation uses service_mode=ServiceMode.TRUCK.

Satisfaction is declared when each detected truck absence triggers exactly one handler invocation and returns an updated or unchanged consistent solution. A violation occurs when pair lookup or timeline recomputation fails; in that case, the handler preserves recoverable state and returns without destructive mutation.

The output of this step is a truck-failure-conditioned pair-local replanning result.

Failure Type 2: Drone-sortie customer not at home.

This operation is performed because absence inside a launched sortie can invalidate only the remaining sortie suffix while leaving already visited prefix decisions irreversible. Once an absent customer is found in the currently launched sortie scan, the engine creates a drone-mode event with sortie index and dispatches it.

Subsequently, the drone-event handler sets the customer absence flag, repairs the current sortie by skip-truncate-reorder logic from the failed position, constructs freeze sets including visited prefix, and then optimizes the remaining pair path. In turn, customers in other launched sorties can be protected via freeze propagation, so one failure may restrict but does not necessarily cancel other pending services. 

\begin{equation}
\mathbb{I}^{\mathrm{drone\_event}}_i
=\mathbb{I}\{i\in\mathcal{C}^{D}_{\text{launched sortie}}\}\cdot(1-\hat{h}_i).
\tag{90}
\end{equation}

In Eq. (90), \mathcal{C}^{D}_{launched sortie} is the active sortie customer list in the launch-scan loop. Event creation uses service_mode=ServiceMode.DRONE and an explicit sortie_index when available.

Satisfaction is declared when the failed customer is resolvable to a valid sortie and repaired suffix stays structurally consistent. A violation occurs when stale sortie indices cannot be relocated or timeline recomputation fails; in that case, the handler returns the pre-event consistent state for that branch.

The output of this step is a repaired sortie and a frozen-prefix-aware local optimization result.

Failure Type 3: Time-window-related infeasibility during online updates.

This step is performed because local repairs and remaining-path optimization can produce candidates that violate temporal constraints even when service-mode events are correctly handled. Once a candidate timeline is recomputed, drone-customer and truck-customer latest-time conditions are checked in hard-constraint routines used by the online optimizer.

Subsequently, infeasible candidates are rejected and search continues from the current feasible incumbent; alternatively, sortie-local repair can skip or truncate problematic suffix customers before global pair updates are attempted. As a result, temporal violations are treated as hard feasibility filters in online mode rather than soft penalties. 

\begin{equation}

\implies
\text{candidate rejected in online ALNS hard-check pipeline}.
\tag{91}
\end{equation}

In Eq. (91), AT(i) is either timeline.truck_arrival[i] or timeline.drone_arrival[i], and l_i is customer.time_window[1]. Rejection path uses all_hard_constraints_satisfied(...) in online mode.

Satisfaction is declared when accepted online updates remain temporally feasible under hard checks. A violation occurs when temporal bounds are exceeded; in that case, the current online incumbent is retained and the violating candidate is discarded.

The output of this step is a temporally feasible accepted update or a safe no-change fallback.

4.4.2 Online replanning trigger decision

Step 1: Trigger-condition evaluation.

This step is performed because online optimization must be invoked only when execution reveals a disruptive event that invalidates the unchanged continuation assumption. Once a not-home condition is detected in truck or drone checks, event dispatch is called immediately in the same traversal iteration.

Subsequently, no accumulation threshold is applied, so each observed failure triggers immediate local handling; in turn, events that cannot be resolved to valid pair/sortie contexts are safely ignored by returning the unchanged solution. As a result, the trigger design is event-immediate rather than batch-thresholded. 

\begin{equation}
\text{Trigger}(k)=
\mathbb{I}^{\mathrm{truck\_event}}(k)
\vee
\mathbb{I}^{\mathrm{drone\_event}}(k).
\tag{92}
\end{equation}

In Eq. (92), the two indicators are constructed from truck-node and launched-sortie scans at traversal position k. The event object carries pair id, customer id, service mode, and optional sortie index.

Q1: trigger occurs at every detected failure, not at a cumulative threshold. Q2: range is determined by event pair id plus frozen-set construction, therefore only the affected pair remainder is optimized. Q3: no-trigger cases include successful service attempts and stale/unresolvable event contexts where handlers return unchanged solutions.

Satisfaction is declared when disruptive events invoke handlers exactly at detection points and non-disruptive states continue without unnecessary optimization overhead. A violation occurs when events are detected but not dispatched; in that case, execution would diverge from implemented logic, and this path is not present in the current code.

The output of this step is a binary control decision between direct continuation and immediate local replanning.

This step is performed because event handling must optimize only the mutable suffix while preserving executed commitments. Once the affected pair is located, executed nodes and launched-sortie commitments are frozen, current repaired pair state is constructed, and lightweight ALNS is called on this constrained pair solution.

Subsequently, the objective on candidate states remains the same global formula interface as offline compute_objective, but the search regime differs because online mode uses strict hard-feasibility acceptance and strict objective improvement only. As a result, objective composition remains consistent at function level while acceptance and neighborhood policies become execution-specific.

\end{equation}

4.4.3 Online re-optimization algorithm

Step 1: Selection of lightweight online optimizer and budget compression analysis.

This step is performed because rerunning full offline ACO-ALNS at each online event would violate real-time response requirements. Once an event has been accepted for handling, the system calls LightweightALNSOptimizer.optimize_remaining_path, which reuses a restricted destroy-repair family but removes SA acceptance, adaptive weights, cross-group periodic moves, and offline-scale nested ant loops.

Subsequently, online iteration and removal budgets are read from params.online_alns, while offline budgets are governed by params.aco.max_iterations, params.aco.ant_count, and params.alns.iterations. In turn, this establishes a strong budget compression that prioritizes latency over global diversification and therefore sacrifices some improvement depth in exchange for immediate feasibility-preserving response. 

\begin{equation}
B_{\mathrm{off}}\approx I_{\mathrm{aco}}\cdot A\cdot L_{\mathrm{alns}},
\qquad
B_{\mathrm{on}}=L_{\mathrm{on}},
\tag{95}
\end{equation}

4.5 Online Feasibility-Preservation Mechanisms

Step 1: Online maintenance of temporal constraints.

This step is performed because realized service outcomes alter departure times and can cascade into downstream lateness if timeline propagation is not recomputed. Once each relevant event mutation has been applied, truck and drone timelines are recomputed and checked against customer latest bounds through hard-feasibility gates.

Subsequently, temporal infeasibility is handled by candidate rejection in online ALNS and by sortie repair attempts in event handlers, rather than by soft acceptance. As a result, online mode enforces strict temporal feasibility on accepted updates while still allowing internal attempted candidates to be filtered out. 

\begin{equation}
\forall i\in\mathcal{N}_T:\;AT_T(i)\le l_i,
\qquad
\forall j\in\mathcal{N}_D:\;AT_D(j)\le l_j.
\tag{98}
\end{equation}

In Eq. (98), truck and drone arrivals correspond to timeline.truck_arrival and timeline.drone_arrival, and l_i is customer.time_window[1]. Cascade handling is operationalized by recomputing timeline and revalidating subsequent sorties after each accepted repair.

Satisfaction is declared when all accepted updates satisfy latest-time bounds for both truck and drone served customers. A violation occurs when any bound is exceeded; in that case, the violating candidate is rejected or the offending sortie is repaired and rechecked.

The output of this step is a temporally feasible online solution trajectory after each accepted mutation.

Step 2: Online maintenance of capacity constraints.

This step is performed because realized not-home outcomes change whether delivery or pickup loads are actually transferred at visited customers. Once timeline truth is known at each visit, truck and drone loads are updated by success-dependent transfer rules, and hard-feasibility checks ensure capacities are never exceeded on accepted states.

Subsequently, if a service fails because the customer is absent, the load update for that customer is skipped, meaning undelivered delivery mass remains onboard and uncollected pickup mass is not loaded. In turn, downstream load states may diverge from offline expectation and require reoptimization to regain feasibility margins. 

\begin{equation}
L^{+}(i)=
\begin{cases}
L^{-}(i)-w_i, & i\in\mathcal{N}^D\ \land\ \hat{h}_i=1,\\
L^{-}(i)+w_i, & i\in\mathcal{N}^P\ \land\ \hat{h}_i=1,\\
L^{-}(i), & \hat{h}_i=0,
\end{cases}
\qquad
L^{+}(i)\le Q.
\tag{99}
\end{equation}

In Eq. (99), L^- and L^+ denote pre/post service loads in load-tracking states, w_i is customer weight, and Q denotes truck or drone capacity as appropriate. Service-failure no-transfer behavior matches update_sortie_load and truck-load update logic under home_status gating.

Satisfaction is declared when all node-level and recovery-transfer loads stay within capacity bounds. A violation occurs when any load exceeds its capacity; in that case, the candidate is rejected or repaired before acceptance.

The output of this step is a load-consistent online state that reflects realized rather than planned transfers.

Step 3: Online feasibility of drone sorties and cancellation/truncation behavior.

This step is performed because online failures inside sorties require localized corrections that may shorten the remaining customer suffix. Once a drone event occurs, the repair pipeline applies infeasible-customer skipping and energy-based truncation from the failed position, and then reorders the active remainder by expected incremental cost.

Subsequently, full sortie cancellation is not enforced as a separate explicit command in the online module; rather, suffix-level cancellation is achieved by truncating the post-failure segment to the largest feasible prefix, while executed or currently failed prefix customers remain fixed by design. As a result, sortie adaptability is suffix-focused and prefix-preserving. 

\begin{equation}
\mathcal{S}^{\mathrm{new}}=
\operatorname{Reorder}\Big(
\operatorname{Truncate}_{E_D}\big(
\operatorname{Skip}_{\mathrm{TW},Q_D}(\mathcal{S}^{\mathrm{old}})\big)
\Big).
\tag{100}
\end{equation}

In Eq. (100), Skip corresponds to apply_b1_skip_infeasible_customers, Truncate corresponds to apply_b2_truncate_sortie, and Reorder corresponds to reorder_remaining_customers. Feasibility checks rely on timeline/load recomputation and sortie-level hard constraints.

Satisfaction is declared when the repaired sortie passes structural, payload, battery, and synchronization checks. A violation occurs when repair cannot produce a feasible modification; in that case, the algorithm keeps the current feasible incumbent state and does not force an infeasible sortie acceptance.

The output of this step is a repaired sortie suffix that respects execution locks and hard constraints.

Step 4: Online enforcement of truck-drone synchronization constraints.

This step is performed because launch-recovery coupling is physically valid only if truck waiting at recovery does not exceed the configured upper bound. Once a sortie timeline is computed, truck waiting is measured at recovery as positive drone-arrival lag beyond truck arrival and is checked against the wait limit.

Subsequently, synchronization overruns are handled through feasibility rejection and repair cycles in online mode so that accepted states remain within wait limits. Consequently, deviation between planned and realized waiting time is tolerated only inside rejected candidate branches, not inside accepted online updates. 

\begin{equation}
W_{\mathrm{truck}}(r)=\max\{0,AT_D(r)-AT_T(r)\},
\qquad
W_{\mathrm{truck}}(r)\le W_{\max}.
\tag{101}
\end{equation}

In Eq. (101), AT_D(r) and AT_T(r) are drone and truck arrivals at recovery node r, and W_max maps to params.constraints.max_truck_wait_time.

Satisfaction is declared when recovery waiting at all sorties remains below or equal to the configured limit. A violation occurs when waiting exceeds the limit; in that case, the associated candidate update is rejected or further repaired before acceptance.

The output of this step is a synchronization-feasible accepted online solution with bounded truck waiting.

4.6 Realized Reporting Structures

Once execution terminates, the engine constructs ExecutionResult with realized timeline dictionary, realized home-status map, failed-customer set, truck-distance and drone-energy traces, actual total cost, and replanning snapshots. Subsequently, this object is consumed by Monte Carlo aggregation and reporting utilities, so online execution remains directly analyzable without rerunning event logic.

4.7 Complexity and Budget Implications

The implemented online solver intentionally compresses neighborhood search to fixed small iterations and limited operators, and therefore each event response cost is approximately linear in online iteration count times candidate evaluation cost for one pair. As a result, the design privileges latency stability under repeated events, while leaving deep global restructuring to the offline stage.

4.8 Consolidated Interpretation

The complete online stage is an event-driven local-repair framework that preserves offline structure, reveals realized uncertainty during traversal, and updates only mutable suffixes under strict feasibility and strict-improvement policies. Consequently, the implementation is consistent with a two-layer methodology in which offline expectation planning and online realized execution are explicitly separated yet computationally coupled through shared state representations.
