Chapter 1 Algorithm Overview

1.1 Algorithm Name and Problem Background

The studied truck-drone collaborative distribution setting targets last-mile service where customer at-home uncertainty causes realized service failures and dynamic schedule disruption. In practical urban operations, static routing plans that ignore this stochastic availability structure frequently produce repeated revisits, extra energy use, and waiting amplification at synchronization nodes. The algorithm therefore addresses the integrated problem of constructing a feasible cooperative plan offline and adapting it online when availability truth is revealed during execution.

The implemented method is a three-stage hybrid framework named an ETPRC-initialized ACO-ALNS with event-driven online replanning, as reflected by the constructive module in src/spd/etprc.py, the offline optimizer in src/spd/aco_alns.py, and the execution-replanning chain in src/spd/simulation.py and src/spd/online.py. Methodologically, it belongs to a two-phase optimization with online recourse architecture: deterministic structure construction and uncertainty-aware expected optimization offline, followed by realization-conditioned local recourse online. Compared with single-stage static heuristics, the distinguishing trait is explicit cross-stage state transfer and freeze-aware local reoptimization after event revelation.

The core innovations are stage-coupled rather than isolated. In the initial stage, the ETPRC pipeline integrates cluster balancing, route construction, sortie extraction, rescue insertion, and probability-aware post-adjustment. In the offline stage, a nested ACO-ALNS design combines global pheromone learning with adaptive local destroy-repair search under hard-feasibility hierarchy. In the online stage, failure-driven local repair and lightweight ALNS operate under frozen executed prefixes, which preserves operational irreversibility while maintaining computational responsiveness.

1.2 Integrated Framework and Three-Stage Relations

The overall logic is a directed information chain from initial construction to offline refinement and then to online execution. First, stage 1 builds a complete structurally feasible cooperative plan candidate from static instance and parameter inputs. Subsequently, stage 2 receives this candidate, refines it by ACO-ALNS, and returns an optimized offline solution object. Finally, stage 3 accepts that optimized solution as the execution baseline, samples and reveals customer availability outcomes, and performs event-triggered local recourse when service failures occur.

Stage 1 takes instance geometry, customer demand types, capacity-energy-time parameters, and probability profiles as input; its core is ETPRC, and its output is a complete initial Solution. Stage 2 takes this initial Solution as input and runs ACO-ALNS to output an optimized offline Solution with refined truck routes and sortie structures. Stage 3 takes that optimized offline Solution as input and executes an online replanning mechanism, whose output is an ExecutionResult containing realized trajectory, realized failures, and realized total cost.

Stages 1 and 2 are offline precomputation layers, while stage 3 is an online real-time response layer. The transition from offline to online happens exactly when planned_solution enters the execution engine. Once this handover has been completed, the decision context switches from expected-value optimization under probability vectors to realized binary availability adaptation under event timing.

Chapter 2 Initial Solution Construction

The initial solution construction phase serves as the entry point of the three-stage algorithm. It receives the static instance, parameter bundle, and probability data and produces one complete feasible cooperative plan candidate. This candidate is not the final answer but the structural baseline for subsequent refinement. Once the constructive phase has been completed, the generated solution is subsequently passed to the offline optimization phase described in Chapter 3.

2.1 Algorithm Overview

The initial solution construction procedure is implemented around ETPRCBuilder.build_initial_solution(). In the current code base, the customer set is first partitioned into geographically compact and delivery-balanced vehicle-pair clusters; a feasible all-truck route is then constructed for each cluster; profitable drone sorties are subsequently extracted from the truck route; temporarily skipped customers are then rescued through cross-pair reinsertion; and a probability-aware post-adjustment stage is finally applied to improve the expected service timing without violating hard feasibility. Therefore, the executable implementation is organized into five consecutive phases rather than a single monolithic heuristic.

The five phases are tightly coupled. Phase I reduces the search space by localized partitioning. Phase II creates a feasible truck backbone for each cluster. Phase III converts part of that backbone into truck-drone cooperation by positive-gain sortie extraction and intra-sortie sequencing. Phase IV attempts to restore any temporarily skipped customer so that complete customer coverage can be recovered whenever possible. Phase V repositions low home-probability visits while preserving hard feasibility through rollback checks. Across these phases, structural constraints, truck capacity constraints, residual customer-time checks, depot return constraints, sortie cardinality constraints, drone payload constraints, drone battery constraints, truck waiting constraints, and global customer-coverage constraints are addressed. Under the current experimental configuration, however, the customer windows are uniformly set to $[0,480]$, so differentiated customer-level time-window effects are largely degenerate and the practically binding conditions in the truck-route stage are more likely to be capacity feasibility and the global 480-minute route horizon.

Recognized phases. Phase I: Customer Partitioning and Delivery-Load Balancing. Phase II: Feasible Truck Route Construction. Phase III: Sortie Extraction and Intra-Sortie Sequencing. Phase IV: Cross-Pair Rescue and Solution Assembly. Phase V: Probability-Aware Post-Adjustment and Final Coverage Enforcement.

2.2 Phase-by-Phase Description

The following five phases describe the executable structure of the implemented initial-solution constructor. For each phase, the operative goal is first stated, after which the detailed steps, the governing equations, the satisfaction and violation conditions, and the corresponding code locations are reported.

2.3 Customer Partitioning and Delivery-Load Balancing

In Phase I, the customer set $\mathcal{N}$ is partitioned into $K$ clusters, where each cluster is intended to serve as the initial working domain of one truck-drone pair. The primary purpose of this phase is to generate geographically compact groups while preventing an obviously overloaded delivery cluster from being passed to the routing stage. In this sense, spatial cohesion is first established, and delivery-load feasibility is then repaired. This phase adapts the classical K-means paradigm [REF].

Step 1: Cluster cardinality and centroid initialization.

The cluster count is set as $K$, where $K$ is taken directly from instance.vehicle_pair_count. A centroid set $\mathcal{M}^{(0)}=\{\mu_1^{(0)},\dots,\mu_K^{(0)}\}$ is then initialized by random sampling from the existing customer coordinates. This operation is performed so that the downstream assignment process is anchored on actual customer locations rather than on synthetic coordinate guesses. 

\begin{equation}
K = \texttt{instance.vehicle\_pair\_count},
\qquad
\mathcal{M}^{(0)} = \{\mu_1^{(0)}, \mu_2^{(0)}, \ldots, \mu_K^{(0)}\}.
\tag{3}
\end{equation}

If $K > |\mathcal{N}|$, repeated sampling from the available customer set is performed until $K$ centroids are obtained. Hence, the state update at the end of this step is the availability of an initialized centroid set and an empty assignment structure for the iterative grouping loop.

Step 2: Iterative customer assignment and centroid update.

Each customer $i \in \mathcal{N}$ with coordinate vector $(x_i, y_i)$ is assigned to its nearest centroid under squared Euclidean distance. The assignment is performed because the route-construction stage benefits from spatially concentrated customer subsets. After the assignment, each centroid is updated to the mean coordinate of its current cluster. The resulting output is the temporary cluster family $\{\mathcal{C}_1^{(t)},\dots,\mathcal{C}_K^{(t)}\}$ and its updated centroid set. 

\begin{equation}
k^{\star}(i) = \arg\min_{k \in \{1,\ldots,K\}} \left[(x_i-\mu_{k,x}^{(t)})^2 + (y_i-\mu_{k,y}^{(t)})^2\right].
\tag{4}
\end{equation}

\begin{equation}
\mu_k^{(t+1)} = \left(
\frac{1}{|\mathcal{C}_k^{(t)}|}\sum_{i \in \mathcal{C}_k^{(t)}} x_i,
\frac{1}{|\mathcal{C}_k^{(t)}|}\sum_{i \in \mathcal{C}_k^{(t)}} y_i
\right).
\tag{5}
\end{equation}

\begin{equation}
\Delta^{(t)} = \sum_{k=1}^{K} \left\| \mu_k^{(t+1)} - \mu_k^{(t)} \right\|_2.
\tag{6}
\end{equation}

The iteration is terminated once $\Delta^{(t)} \le \varepsilon$, where $\varepsilon$ is the internal tolerance represented by _EPS, or once the configured iteration cap is reached. Satisfaction is therefore declared when the centroid shift becomes negligible; otherwise, another assignment-update iteration is performed.

Code location. src/spd/etprc.py::ETPRCBuilder._customer_grouping.

Step 3: Empty-cluster repair.

Whenever an empty cluster is detected, one customer is removed from the largest donor cluster and is transferred to the empty recipient cluster. The transferred customer is selected as the farthest customer from the donor centroid. This operation is performed because the later pair-wise route construction assumes that each vehicle pair is associated with a concrete customer subset. The output of this step is a non-empty assignment pattern whenever the donor cluster contains more than one customer. 

\begin{equation}
i^{\star} = \arg\max_{i \in \mathcal{C}_{d}} \left\| (x_i, y_i) - \mu_{d} \right\|_2,
\qquad
\mathcal{C}_{e} \leftarrow \mathcal{C}_{e} \cup \{i^{\star}\},
\qquad
\mathcal{C}_{d} \leftarrow \mathcal{C}_{d} \setminus \{i^{\star}\}.
\tag{7}
\end{equation}

A repair is feasible only when the donor cluster has cardinality greater than one. Otherwise, the empty cluster cannot be repaired in that iteration, and the previous centroid is retained. Hence, the state is updated by enforced non-emptiness whenever a valid donor exists.

Code location. src/spd/etprc.py::ETPRCBuilder._customer_grouping.

Step 4: Delivery-load balancing across clusters.

After the geometric partition has converged, a delivery-load repair is performed. For each cluster $\mathcal{C}_k$, the delivery-only weight is computed as $W_k^D$. If $W_k^D > Q_T$, where $Q_T$ denotes truck capacity, the farthest delivery customer in the overloaded cluster is considered for reassignment to the nearest feasible recipient cluster. The purpose is to remove obviously infeasible delivery mass before the route stage is entered. 

\begin{equation}
W_k^D = \sum_{i \in \mathcal{C}_k \cap \mathcal{N}^D} w_i,
\qquad
W_k^D \le Q_T \quad \text{must hold for cluster-level delivery feasibility}.
\tag{8}
\end{equation}

\begin{equation}
k' = \arg\min_{r \in \mathcal{R}(i)} \left\| (x_i,y_i) - \bar{\mu}_r \right\|_2,
\qquad
\mathcal{R}(i)=\left\{r \ne k : W_r^D + w_i \le Q_T \right\}.
\tag{9}
\end{equation}

Satisfaction is achieved when every cluster obeys $W_k^D \le Q_T$. A violation occurs whenever no feasible recipient cluster exists for a removable delivery customer; in that case, the cluster remains unchanged in the current pass. The resulting output is the balanced group family $\{\mathcal{C}_1,\dots,\mathcal{C}_K\}$.

2.4 Feasible Truck Route Construction

In Phase II, an all-truck route is constructed for each cluster $\mathcal{C}_k$ by a cheapest-feasible-insertion mechanism equipped with a deadlock fallback and a retry pass. This phase is intended to produce a temporally feasible and load-feasible truck backbone from which drone sorties can later be extracted. The route is therefore not treated as the final service plan; rather, it is used as a feasible scaffold for the subsequent truck-drone decomposition. In the current experiments, because every customer shares the same window $[0,480]$, the practically decisive conditions in this phase are not customer-specific time-window differences but truck-load feasibility and compliance with the global depot-return horizon. This mechanism follows the logic of classical cheapest-insertion heuristics [REF].

Step 1: Route and load-state initialization.

For each cluster $\mathcal{C}_k$, a partial route $R_k$ is initialized as the depot-only sequence $[0]$, and the uninserted set is initialized as $\mathcal{U}_k = \mathcal{C}_k$. The initial truck load is computed as the total delivery mass assigned to the cluster. This initialization is performed because the delivery parcels must be loaded before the first truck movement is simulated. The output is the initial state $(R_k, \mathcal{U}_k, L_k^{(0)})$. 

\begin{equation}
R_k^{(0)} = [0],
\qquad
\mathcal{U}_k^{(0)} = \mathcal{C}_k,
\qquad
L_k^{(0)} = \sum_{i \in \mathcal{C}_k \cap \mathcal{N}^D} w_i.
\tag{10}
\end{equation}

The initialization is valid only if $L_k^{(0)} \le Q_T$; otherwise, the candidate route would already violate truck capacity before any movement is performed. In the implementation, this condition is checked inside the route-feasibility routine.

Code location. src/spd/etprc.py::ETPRCBuilder._build_truck_route.

Step 2: Cheapest feasible insertion evaluation.

For each uninserted customer $i \in \mathcal{U}_k$ and each insertion position $p$ in the current route, an insertion cost is evaluated. The cost combines a truck-distance increment and a time-window tightness penalty. The purpose is to identify the insertion that is simultaneously economical and less likely to endanger the temporal feasibility of later route segments. The output is the best feasible insertion pair $(i^{\star}, p^{\star})$, if such a pair exists. 

\begin{equation}
\Delta c_{i,p} = \omega_d \left[d_T(r_{p-1}, i) + d_T(i, r_p) - d_T(r_{p-1}, r_p)\right]
+ \omega_{tw} \left(\frac{1}{\max(l_i - e_i, 0.01)}\right).
\tag{11}
\end{equation}

\begin{equation}
a_h = \delta_{h-1} + \frac{d_T(r_{h-1}, r_h)}{v_T},
\qquad
\delta_h = \max(a_h, e_{r_h}) + s_{r_h}.
\tag{12}
\end{equation}

\begin{equation}
L_h =
\begin{cases}
L_{h-1} - w_{r_h}, & r_h \in \mathcal{N}^D, \\
L_{h-1} + w_{r_h}, & r_h \in \mathcal{N}^P.
\end{cases}
\tag{13}
\end{equation}

\begin{equation}
a_h \le l_{r_h},
\qquad
L_h \le Q_T,
\qquad
\delta_{|R_k|} + \frac{d_T(r_{|R_k|}, 0)}{v_T} \le t_0^{\max}.
\tag{14}
\end{equation}

Satisfaction is declared when all inequalities in (12) hold for the candidate route. A violation occurs when any customer is reached after its latest time, the truck load exceeds $Q_T$, or the depot return time exceeds $t_0^{\max}$. Under the current uniform-window setting $[0,480]$, the first condition is usually non-binding at the customer-discrimination level, whereas the second and third conditions remain active and are the more plausible reasons why no insertion position can be found. Among all feasible insertions, the minimum-cost one is selected and appended to the route state.

Code location. src/spd/etprc.py::ETPRCBuilder._build_truck_route, especially the internal routines is_route_feasible() and _try_insert_one().

Step 3: Deadlock fallback, skipping, and retry.

If no feasible insertion can be identified over the current route, a deadlock fallback is activated. The remaining customers are ranked by ascending time-window width $\Delta_i^{tw}=l_i-e_i$, and the tightest customer is attempted first. This is performed because a customer with a narrow temporal slack is the least likely to remain insertable if it is postponed. Under the present configuration, however, all customers share the same width $480$, so this ordering is effectively degenerate and the fallback behaves more like a tie-broken retry rule than a genuinely time-window-sensitive prioritization rule. If the fallback still fails, the selected customer is temporarily skipped and is reconsidered in a retry pass after the route backbone has been completed. 

\begin{equation}
i^{\mathrm{tight}} = \arg\min_{i \in \mathcal{U}_k} (l_i - e_i).
\tag{15}
\end{equation}

\begin{equation}
\mathcal{S}_k^{\mathrm{skip}} \leftarrow \mathcal{S}_k^{\mathrm{skip}} \cup \{ i^{\mathrm{tight}} \},
\qquad
\mathcal{U}_k \leftarrow \mathcal{U}_k \setminus \{ i^{\mathrm{tight}} \}.
\tag{16}
\end{equation}

In the retry pass, skipped customers are revisited in descending time-window width order, as implemented in the code. Because the widths are identical in the current experiments, the retry order is again effectively neutral with respect to time-window differentiation. Therefore, if customers remain skipped after the retry pass, the more plausible causes are route-horizon infeasibility or truck-load infeasibility rather than customer-specific temporal ordering. The state update at the end of this step is a closed all-truck route $R_k = [0, \ldots, 0]$ together with a residual skipped set, if any customers still cannot be reinserted.

Code location. src/spd/etprc.py::ETPRCBuilder._build_truck_route.

2.5 Sortie Extraction and Intra-Sortie Sequencing

In Phase III, each all-truck route is converted into a cooperative truck-drone plan by identifying customer subsets whose removal from the truck route yields a positive objective gain. This phase is not executed by a direct local distance rule. Instead, the current implementation enumerates launch-recovery pairs, evaluates customer subsets between them, optimizes the internal service order of each subset, and retains only those sortie candidates that improve the offline objective. Under the current uniform-window setting, the sortie stage still preserves customer latest-time checks, but these checks are less discriminative than the battery, payload, truck-wait, and recovery-load constraints. Consequently, a profit-screened and feasibility-protected sortie set is produced.

Step 1: Baseline definition and candidate subset enumeration.

For a route $R_k$, a baseline pair solution with no drone sortie is first defined, and its scalar objective value is denoted by $Z_0$. A launch node $u$ and a recovery node $v$ are then selected such that $u$ appears before $v$ on the route. The intermediate node set $\mathcal{B}(u,v)$ is scanned, and candidate subsets are formed subject to sortie-size and individual drone-capacity filters. The operation is performed because only customers embedded between a feasible launch-recovery pair can be extracted without changing the truck backbone arbitrarily. 

\begin{equation}
\mathcal{B}(u,v) = \left\{ i \in R_k : \operatorname{pos}_{R_k}(u) < \operatorname{pos}_{R_k}(i) < \operatorname{pos}_{R_k}(v) \right\}.
\tag{17}
\end{equation}

\begin{equation}
S \subseteq \left\{ i \in \mathcal{B}(u,v) : w_i \le Q_D \right\},
\qquad
1 \le |S| \le m_{\max}.
\tag{18}
\end{equation}

Satisfaction is declared when a subset obeys the cardinality bound $|S| \le m_{\max}$ and each candidate customer satisfies the individual weight screen $w_i \le Q_D$. The output is a finite pool of launch-recovery-subset candidates to be further evaluated.

Code location. src/spd/etprc.py::ETPRCBuilder._extract_sorties.

Step 2: Intra-sortie order optimization.

For every candidate subset $S$, all customer permutations $\pi \in \Pi(S)$ are enumerated. A sortie $s=(u,\pi,v)$ is constructed on the simplified pair route $[0,u,v,0]$, and the permutation is retained only if structure feasibility, synchronized timeline feasibility, truck-load feasibility, drone-payload feasibility, drone-energy feasibility, truck-wait feasibility, and drone-arrival time-window feasibility are satisfied. The purpose is to ensure that the customer order is not assumed but is optimization-based. The output is the best feasible permutation $\pi^{\star}$, if one exists. 

\begin{equation}
\pi^{\star} = \arg\min_{\pi \in \Pi(S)} Z(u, \pi, v)
\quad
\text{s.t.}
\quad
\texttt{check\_sortie\_structure} = \text{True},
\quad
\texttt{check\_sortie\_feasibility} = \text{True}.
\tag{19}
\end{equation}

A violation occurs whenever any candidate permutation breaks launch-recovery ordering, sortie structure, payload progression, energy capacity, truck wait, or time-window admissibility. In such a case, the permutation is discarded. If all permutations are infeasible, the original customer order is returned by the implementation as a deterministic fallback.

Code location. src/spd/etprc.py::ETPRCBuilder._optimize_sortie_order; support routines: src/spd/core.py::check_sortie_structure, compute_truck_timeline, compute_truck_load, check_sortie_feasibility, and compute_objective.

Step 3: Positive-gain evaluation and greedy sortie selection.

Once a feasible sortie candidate has been constructed, the customers of $S$ are removed from the truck route to form a candidate pair, and the objective improvement is computed relative to the all-truck baseline. Only candidates with positive gain are retained. The surviving candidates are then sorted by descending gain and are greedily selected under a set of conflict-exclusion rules. This is performed because a jointly optimal selection is not solved exactly in the implementation; instead, a gain-ranked greedy schedule is used. 

\begin{equation}
\Delta Z(s) = Z_0 - Z_s.
\tag{20}
\end{equation}

\begin{equation}
\Delta Z(s) > 0
\quad \text{must hold for selection eligibility.}
\tag{21}
\end{equation}

\begin{equation}
S(s) \cap \mathcal{D}^{\mathrm{sel}} = \varnothing,
\qquad
\{u,v\} \cap \mathcal{D}^{\mathrm{sel}} = \varnothing,
\qquad
u \notin \mathcal{L}^{\mathrm{sel}},
\qquad
v \notin \mathcal{R}^{\mathrm{sel}}.
\tag{22}
\end{equation}

\begin{equation}
\operatorname{pos}_{R_k'}(u) < \operatorname{pos}_{R_k'}(v).
\tag{23}
\end{equation}

Satisfaction is declared when the gain is positive and the customer, anchor-node, and launch/recovery conflicts are absent. A violation occurs when a candidate overlaps with already selected drone customers, consumes an existing launch or recovery anchor, or breaks the current route order. The state output is the tuple $(R_k', \mathcal{S}_k, \mathcal{T}_k, \mathcal{D}_k)$ consisting of the updated truck route, the selected sortie list, the truck-customer set, and the drone-customer set.

Code location. src/spd/etprc.py::ETPRCBuilder._extract_sorties; support objective and feasibility routines are located in src/spd/core.py.

2.6 Cross-Pair Rescue and Solution Assembly

In Phase IV, customers that remain uninserted after the cluster-wise route construction stage are collected into a global skipped set and are re-examined through cross-pair insertion. The goal is to recover customer coverage without discarding already constructed pair solutions. This phase is necessary because the route builder is allowed to skip customers temporarily when local feasibility deadlocks are encountered, yet the overall constructive heuristic attempts to end with a complete assignment whenever a consistent reinsertion can still be found. In the present configuration, the rescue stage should again be interpreted primarily as a response to route-duration and capacity pressure, not as a response to heterogeneous customer windows.

Step 1: Aggregation and ordering of skipped customers.

Let $\mathcal{U}^{\mathrm{skip}}$ denote the union of all skipped customers returned by the Phase II route builder. In the implementation, these customers are processed in descending order of time-window width rather than in ascending order. This ordering is performed so that less urgent customers are considered first in the cross-pair rescue loop. The resulting state is an ordered rescue candidate list. 

\begin{equation}
\mathcal{U}^{\mathrm{skip}} = \bigcup_{k=1}^{K} \mathcal{S}_k^{\mathrm{skip}},
\qquad
i_1, i_2, \ldots \text{ are sorted by } (l_i - e_i) \text{ in descending order.}
\tag{24}
\end{equation}

No feasibility is decided at this step. Only the global rescue order is defined, and the output is the ordered skipped-customer sequence.

Code location. The rescue loop is implemented inside src/spd/etprc.py::ETPRCBuilder.build_initial_solution.

Step 2: Cross-pair insertion search with anchor preservation.

For each skipped customer $i \in \mathcal{U}^{\mathrm{skip}}$, every pair route and every insertion position are examined. The same insertion-cost form as in Phase II is used. However, at this rescue step, explicit route-time feasibility and depot-return feasibility are checked, and the existing sortie anchors are preserved by requiring every already selected launch node and recovery node to remain on the route with the same precedence relation. This operation is performed because skipped customers must be reintroduced without destroying an already valid sortie skeleton. 

\begin{equation}
\Delta c_{i,p}^{\mathrm{res}} = \omega_d \left[d_T(r_{p-1}, i) + d_T(i, r_p) - d_T(r_{p-1}, r_p)\right]
+ \omega_{tw} \left(\frac{1}{\max(l_i - e_i, 0.01)}\right).
\tag{25}
\end{equation}

\begin{equation}
a_h \le l_{r_h},
\qquad
\delta_{|R_p|} \le t_0^{\max},
\qquad
\operatorname{pos}_{R_p'}(l(s)) < \operatorname{pos}_{R_p'}(r(s)) \quad \forall s \in \mathcal{S}_p.
\tag{26}
\end{equation}

Satisfaction is declared when the candidate route remains temporally feasible and every existing sortie anchor pair remains present and correctly ordered. A violation occurs if any anchor disappears or is reversed. Under the current $[0,480]$ setting, the temporal part of this test mainly acts as a route-horizon filter rather than as a differentiated customer-window filter. It should be noted that the rescue loop does not explicitly recompute truck-load feasibility inside this local test; instead, the implemented acceptance rule is restricted to the conditions written above. The output is either a rescued customer assignment to one pair or a residual skipped status.

Code location. The rescue block inside src/spd/etprc.py::ETPRCBuilder.build_initial_solution.

Step 3: Global solution assembly.

Once all pair-level routes and sorties have been finalized, the global assignment set is assembled, and a Solution object is created. The purpose of this step is to establish a uniform global representation that can be passed to the probability-adjustment stage and to the downstream ACO/ALNS solvers. The resulting output is the intermediate solution $\mathcal{S}^{(0)}$ together with an explicit unserved-customer set. 

\begin{equation}
\mathcal{A} = \bigcup_{k=1}^{K} \left( \mathcal{T}_k \cup \mathcal{D}_k \right),
\qquad
\mathcal{U} = \mathcal{N} \setminus \mathcal{A} \; \cup \; \mathcal{U}^{\mathrm{skip,res}}.
\tag{27}
\end{equation}

Satisfaction is achieved when $\mathcal{U}=\varnothing$. If $\mathcal{U}\neq\varnothing$ at this intermediate point, the solution is still passed to Phase V, and a final failure is raised only after the probability-aware post-adjustment has been completed.

Code location. src/spd/types.py::Solution and the assembly block in src/spd/etprc.py::ETPRCBuilder.build_initial_solution.

2.7 Probability-Aware Post-Adjustment and Final Coverage Enforcement

In Phase V, the constructed solution is copied and is then adjusted according to arrival-time-dependent home probabilities. The phase is intended to improve the expected visit timing of low-probability customers while preserving global hard feasibility through immediate rollback. Therefore, the adjustment is not applied greedily without validation; each replacement candidate is evaluated against the full current solution before it is accepted. This phase should not be interpreted as the primary source of the skip phenomenon observed in Phase II; rather, it is a post-construction refinement layer applied after a candidate initial solution has already been assembled.

Step 1: Pair cloning, arrival-time evaluation, and probability ranking.

A deep copy of every pair route, sortie list, truck-customer set, and drone-customer set is first created. For each customer $i$ in a pair, the planned arrival time $a_i$ is computed on the all-home timeline, the corresponding slot index $\tau(i)$ is identified, and the visit probability $p_i$ is read from the customer profile. The customers are then ranked in ascending order of $p_i$. This operation is performed because low-probability visits must be addressed first if the expected service reliability is to be improved. 

\begin{equation}
\tau(i) = \texttt{map\_time\_to\_slot}(a_i),
\qquad
p_i = h_{i,\tau(i)},
\qquad
p_i < p_{\mathrm{th}} \Rightarrow i \text{ is eligible for adjustment},
\tag{28}
\end{equation}

\begin{equation}
p_{\mathrm{th}} = 0.3.
\tag{29}
\end{equation}

If a low-probability customer $i$ is truck-served, the customer is temporarily removed from the route, and every reinsertion position is examined. The arrival probability induced by each candidate position is computed, and the best-improving position is retained. This operation is performed because truck customers can only have their arrival slot changed by route-position modification. The output is a candidate pair with improved $p_i$, if such a pair exists.

\quad \text{s.t.} \quad

\tag{30}
\end{equation}

Satisfaction is declared only when the full-solution hard-feasibility checker accepts the modified pair. A violation occurs when the probability is improved locally but the global solution becomes infeasible; in that case, the candidate is rolled back immediately. \pi_{s}^{\star} = \arg\min_{\pi \in \Pi(S_s)} Z(l(s), \pi, r(s))
\quad \text{s.t.} \quad
\texttt{all\_hard\_constraints\_satisfied} = \text{True}.
\tag{31}
\end{equation}

Satisfaction is declared only when the reordered sortie improves the candidate order and the full solution remains hard-feasible after replacement. A violation occurs when the permutation changes but the feasibility rollback test fails. Therefore, sortie resequencing is feasibility-dominant rather than probability-dominant.

Chapter 3 Offline Optimization

Building upon the initial solution constructed in Chapter 2, the offline optimization phase employs ACO-ALNS to refine solution quality under expected-cost objectives and hard-feasibility controls. The input to this phase is the complete initial Solution, and the output is an optimized offline Solution with updated truck-drone assignment structure. 3.1 Offline Problem Definition and Objective Function

The offline stage occupies the planning layer of the complete system. First, it constructs a deterministic service plan under the all-home assumption used by the planner interface; subsequently, this plan is passed to the online execution and replanning layer, where customer absence events are handled without rerunning the full offline optimization. Consequently, the offline algorithm is not merely a route generator but a structure-producing stage that determines the baseline truck route, the drone sortie structure, the planned arrival sequence, and the cost-risk tradeoff that later shapes online behavior.

Within this offline stage, the algorithm is organized as a nested hybrid procedure. The ACO component forms the outer global search shell and is responsible for solution construction, ant diversification, and pheromone-based learning over truck arcs. Once one ant has produced a complete candidate, the ALNS component in turn acts as a local intensification engine, perturbing and reconstructing the current assignment by destroy-repair search. As a result, ACO is used as the global constructive and learning mechanism, whereas ALNS is used as the adaptive local improvement mechanism.

The present chapter is therefore arranged from model semantics to executable mechanics. The discussion first formalizes the optimization target and the operational constraints that are actually enforced in code. Once this mathematical basis has been established, the exposition turns to the ACO outer loop, then to the ALNS inner loop, then to operator design, acceptance logic, stopping conditions, parameter interaction, and finally algorithm-level pseudocode. In this way, the reader can reconstruct the implemented algorithm without returning to source code.

3.2 Decision Variables

Step 1: Truck arc-usage variable and pair-level route state.

This step is performed because the ACO layer learns over directed truck arcs rather than over whole-route permutations. In the executable implementation, the truck route of each vehicle pair is stored as an ordered node sequence, yet the optimization logic of route cost, pheromone update, and feasibility checking is naturally interpreted in terms of binary arc usage. Consequently, the route sequence must be understood through an equivalent arc-decision view.

Let \(x_{pij}\) denote whether vehicle pair \(p\) uses directed truck arc \((i,j)\). The route of pair \(p\) is therefore the ordered realization of all arcs with \(x_{pij}=1\). Once a route has been constructed, truck travel cost, pheromone deposition, and all route-level feasibility checks are subsequently evaluated by traversing consecutive node pairs along this ordered state. 

\begin{equation}
x_{pij} \in \{0,1\}, \qquad
x_{pij}=1 \iff \text{vehicle pair } p \text{ traverses directed truck arc } (i,j).
\tag{34}
\end{equation}

In Eq. (1), \(p\) indexes vehicle pairs, and \(i\) and \(j\) denote nodes in the depot-customer network. In code, the corresponding state is not stored as an explicit binary tensor but as VehiclePairSolution.truck_route, whose adjacent node pairs define the active arcs.

Satisfaction is declared when the truck route starts and ends at the depot, preserves a valid node order, and induces a route for which all route-level feasibility checks can be computed. A violation occurs when a route is empty, structurally broken, or yields infeasible arrival/load states; in that case, the candidate is either rebuilt, rejected in the pre-check stage, or blocked from becoming the returned best solution.

The output of this step is an arc-based interpretation of the pair route that can be used consistently by the objective, pheromone, and feasibility modules.

3.3 Complete Objective Function

Step 1: Aggregate objective composition.

This step is performed because the offline optimizer must trade off direct operating cost against service reliability and temporal quality. A route with low distance cost but high expected failure exposure is not desirable, and a structurally complete solution that leaves customers unserved must be penalized even if its nominal operating cost is small. Consequently, the implemented objective is deliberately composite rather than purely distance-based.

The complete offline objective adds fixed pair cost, truck distance cost, drone energy cost, expected failed-service cost, a dynamically weighted tardiness penalty, and an explicit unserved-customer penalty. Once these terms are assembled, the resulting scalar objective becomes the common quantity used by ALNS destroy-repair selection, SA acceptance, and ACO best-solution comparison. 

\begin{equation}
\min Z =
Z_{\mathrm{fixed}} + Z_{\mathrm{truck}} + Z_{\mathrm{drone}}
+ Z_{\mathrm{fail}}^{\mathrm{exp}}
+ \beta Z_{\mathrm{tw}}
+ Z_{\mathrm{unserved}}.
\tag{39}
\end{equation}

In Eq. (6), \(Z_{\mathrm{fixed}}\) is the fixed pair cost, \(Z_{\mathrm{truck}}\) is the truck travel cost, \(Z_{\mathrm{drone}}\) is the drone energy cost, \(Z_{\mathrm{fail}}^{\mathrm{exp}}\) is the expected failed-service cost, \(Z_{\mathrm{tw}}\) is the aggregate tardiness term, \(Z_{\mathrm{unserved}}\) is the explicit incompleteness penalty, and \(\beta\) is the dynamic time-window penalty coefficient. In code, the corresponding accumulator variables are z_fixed, z_truck, z_drone, z_fail_expected, z_tw_penalty, and z_unserved_penalty.

Satisfaction is declared when the total objective can be evaluated from a structurally coherent solution and its induced timeline states. A violation occurs when the timeline or structural solution cannot be evaluated; in that case, the objective call raises an exception and the candidate is treated as invalid by the outer optimizer.

The output of this step is one scalar offline objective value that summarizes cost, reliability, and temporal performance under the current candidate.

Step 2: Fixed-pair, truck-travel, and drone-energy cost terms.

This step is performed because the optimizer must first account for the direct operational expenditure induced by using vehicle pairs, traversing truck arcs, and executing drone sorties. These are the baseline physical cost terms from which more uncertainty-aware penalties are subsequently layered.

The fixed cost scales with the number of used vehicle pairs, the truck cost scales with total truck distance, and the drone cost scales with sortie energy converted into monetary expenditure. Once these direct cost terms have been accumulated, the optimizer can in turn compare whether local structural changes reduce actual operational burden before reliability penalties are considered. 

\begin{equation}
Z_{\mathrm{fixed}} = \alpha \cdot |\mathcal{P}_{\mathrm{used}}|.
\tag{40}
\end{equation}

\begin{equation}
Z_{\mathrm{truck}} = c_T \sum_{(i,j)\in \mathcal{A}_T} d^T_{ij}.
\tag{41}
\end{equation}

\begin{equation}
Z_{\mathrm{drone}} = c_E \sum_{s\in \mathcal{S}} E_s.
\tag{42}
\end{equation}

In Eqs. (7) to (9), \(\alpha\) is the fixed pair cost (params.cost.fixed_pair_cost), \(\mathcal{P}_{\mathrm{used}}\) is the set of used vehicle pairs (solution.used_vehicle_pairs), \(c_T\) is the truck cost per kilometer (truck_cost_per_km), \(d^T_{ij}\) is truck distance on arc \((i,j)\), \(c_E\) is the drone energy cost per Wh (drone_energy_cost_per_wh), \(\mathcal{S}\) is the set of sorties, and \(E_s\) is sortie energy computed by compute_sortie_energy.

Satisfaction is declared when all used arcs and all sorties admit valid distance and energy evaluation. A violation occurs when a route arc or sortie state cannot be evaluated; in that case, the enclosing objective evaluation fails and the candidate is rejected by the optimizer.

The output of this step is the operational baseline cost \((Z_{\mathrm{fixed}}+Z_{\mathrm{truck}}+Z_{\mathrm{drone}})\) for the current candidate.

Step 3: Expected-failure penalty under slot-wise home probability.

This step is performed because the offline plan is computed before actual home-presence realization is observed. The optimizer therefore cannot rely solely on deterministic travel cost; instead, it estimates the expected cost of unsuccessful first-attempt service using the planned arrival slot and the customer-specific home-probability profile. This design directly couples route timing and customer risk.

The implementation first computes planned arrival times under the all-home assumption, maps each arrival time into a bounded slot index, and then reads the slot probability from the instance data. Subsequently, the complement probability \(1-p_c(t_c^\ast)\) is multiplied by the failure penalty of customer \(c\), and these terms are summed over all served customers. 

\begin{equation}
Z_{\mathrm{fail}}^{\mathrm{exp}}
=
\sum_{c\in \mathcal{N}_{\mathrm{served}}}
\left(1-p_c(t_c^\ast)\right) Z_{\mathrm{fail}}(c).
\tag{43}
\end{equation}

\begin{equation}
Z_{\mathrm{fail}}(c)=2\,d^T_{0c}\,c_T.
\tag{44}
\end{equation}

In Eqs. (10) and (11), \(p_c(t_c^\ast)\) is the home probability of customer \(c\) at planned arrival slot \(t_c^\ast\), \(d^T_{0c}\) is the truck distance from depot to customer \(c\), and \(c_T\) is truck cost per kilometer. In code, the slot mapping is performed by map_time_to_slot, and the expected-failure term is accumulated in compute_expected_failure_cost.

Satisfaction is declared when each served customer has a valid planned arrival time and a valid slot probability entry. A violation occurs when the timeline or slot access fails; in that case, the objective evaluation is not accepted for optimization use.

The output of this step is a reliability-aware risk surcharge that penalizes planned service at low-probability arrival slots.

Step 4: Dynamic time-window penalty term.

This step is performed because the ALNS inner search intentionally allows some temporally imperfect candidates to remain in the search trajectory rather than rejecting all time-window violations immediately. The objective therefore incorporates a soft tardiness term weighted by a dynamic coefficient \(\beta\), which grows across ACO outer iterations.

For each served customer, the algorithm computes tardiness as the positive excess of arrival time over the latest allowable time. These tardiness values are then summed and multiplied by the current \(\beta\). Once this term has been increased over outer iterations, late-stage search becomes progressively less tolerant of temporal violations. 

\begin{equation}
Z_{\mathrm{tw}} = \sum_{c\in \mathcal{N}_{\mathrm{served}}}\max(0, a_c-l_c).
\tag{45}
\end{equation}

\begin{equation}
\beta_{k+1} = \min(\gamma_{\beta}\beta_k,\beta_{\max}).
\tag{46}
\end{equation}

In Eqs. (12) and (13), \(a_c\) is the planned arrival time of customer \(c\), \(l_c\) is its latest allowable time, \(\gamma_{\beta}\) is the multiplicative growth factor (params.beta_schedule.gamma_beta), and \(\beta_{\max}\) is the upper bound (params.beta_schedule.beta_max). In code, the instantaneous penalty is accumulated in z_tw_penalty, and the schedule update is performed in ACOALNSSolver.advance_beta_schedule.

Satisfaction is declared when all customer arrivals remain at or before their latest times, in which case \(Z_{\mathrm{tw}}=0\). A violation occurs when any arrival exceeds its latest time; in that case, the candidate is not necessarily discarded immediately, but receives a larger objective value and is subsequently filtered by SA acceptance and hard-feasible best gating.

The output of this step is a soft temporal penalty term that connects early exploration to late-stage temporal refinement.

Step 5: Unserved-customer penalty and cross-term tradeoff analysis.

This step is performed because destroy-repair search may temporarily remove customers from the assignment. Without an explicit incompleteness penalty, a candidate could appear artificially attractive merely because it drops difficult customers. The implementation therefore adds a strong penalty to every unserved customer so that incomplete solutions are not misinterpreted as genuine improvements.

The penalty is defined as twice the failed-service penalty of each unserved customer. Consequently, a customer that is dropped from service imposes a surcharge exceeding the basic failure estimate, thereby discouraging the optimizer from using incompleteness as a cost-reduction shortcut. Once this term has been included, the composite objective balances operational expenditure, reliability, timeliness, and completeness in a single scalar. 

\begin{equation}
Z_{\mathrm{unserved}}
=
\sum_{c\in \mathcal{N}_{\mathrm{unserved}}} 2\,Z_{\mathrm{fail}}(c).
\tag{47}
\end{equation}

In Eq. (14), \(\mathcal{N}_{\mathrm{unserved}}\) is the set of currently unserved customers, and the multiplier \(2\) is hard-coded in the implementation rather than exposed as a separate parameter. In code, the corresponding accumulator is z_unserved_penalty.

Satisfaction is declared when the solution serves all customers and thus the unserved penalty is zero. A violation occurs when one or more customers remain in solution.unserved_customers; in that case, the objective is increased sharply and fallback rebuild may also be triggered upstream in the ALNS loop.

The output of this step is a completeness-preserving regularization term that prevents false objective improvement by customer dropping. When Eqs. (7) to (14) are read together, the objective can be interpreted as a deliberate compromise: the fixed, travel, and energy terms reward operational economy, whereas the expected-failure, tardiness, and unserved terms penalize plans that are cheap only because they are temporally weak, reliability-exposed, or incomplete.

3.4 Constraints

Step 1: Drone energy constraint F1.

This step is performed because every sortie must be executable within the physical battery capacity of the drone. Once sortie energy has been computed from flight, waiting, service, and hover states, the algorithm can subsequently determine whether the sortie is physically executable.

\begin{equation}
E_s \le E_D.
\tag{48}
\end{equation}

In Eq. (15), \(E_s\) is sortie energy and \(E_D\) is drone battery capacity (params.energy.drone_battery_capacity).

Satisfaction is declared when every sortie energy remains at or below battery capacity. A violation occurs when one sortie exceeds \(E_D\); in that case, the candidate fails sortie feasibility and is either rejected by hard-feasibility checking or rejected by the structural-and-physical pre-check.

The output of this step is a binary physical-feasibility judgment for every sortie under the battery model.

Code location. src/spd/core.py::check_sortie_feasibility, called by src/spd/core.py::all_hard_constraints_satisfied; energy computed by src/spd/core.py::compute_sortie_energy.

Step 2: Drone payload constraint F2.

This step is performed because a sortie may visit multiple customers and the carried load changes after each service. The payload trajectory must therefore be validated along the sortie sequence rather than only at launch.

\begin{equation}
\ell_{sk}^{D} \le Q_D, \qquad \forall k \text{ along sortie } s.
\tag{49}
\end{equation}

In Eq. (16), \(\ell_{sk}^{D}\) is drone load at sortie stage \(k\), and \(Q_D\) is drone capacity (params.vehicle.drone_capacity).

Satisfaction is declared when the load never exceeds \(Q_D\) during sortie execution. A violation occurs when any intermediate load exceeds capacity; in that case, the sortie fails feasibility and the candidate is not allowed to pass the hard-feasibility layer.

The output of this step is a load-feasibility verdict for the sortie payload trajectory.

Code location. src/spd/core.py::check_sortie_load_feasibility, called by src/spd/core.py::check_sortie_feasibility.

Step 3: Truck waiting constraint F3.

This step is performed because truck-drone synchronization requires bounded truck waiting at the recovery node. Excessive waiting would indicate that the sortie is operationally misaligned with the truck backbone.

\begin{equation}
\max\!\left(0, a_{\mathrm{rec}}^D-a_{\mathrm{rec}}^T\right) \le W_{\max}.
\tag{50}
\end{equation}

In Eq. (17), \(a_{\mathrm{rec}}^D\) and \(a_{\mathrm{rec}}^T\) are drone and truck arrival times at the recovery node, and \(W_{\max}\) is the maximum truck waiting time (params.constraints.max_truck_wait_time).

Satisfaction is declared when truck waiting at recovery does not exceed \(W_{\max}\). A violation occurs when the drone returns too late; in the full hard-feasibility layer, this makes the sortie infeasible, whereas in the structural-and-physical pre-check this condition is only logged and intentionally not used as an immediate rejection trigger. Consequently, the pre-check and the final hard-feasibility layer do not use exactly the same strictness here.

The output of this step is a synchronization-feasibility judgment whose treatment depends on the active checking layer.

Code location. src/spd/core.py::check_sortie_feasibility, called by src/spd/core.py::all_hard_constraints_satisfied; relaxed handling in src/spd/aco_alns.py::_structural_and_physical_check, called by src/spd/aco_alns.py::ALNSOptimizer.optimize.

Step 4: Drone customer time-window constraint F4.

This step is performed because a drone-served customer must still be visited within its time window. Temporal feasibility must therefore be checked against drone arrival times, not only against truck arrival times.

\begin{equation}
a_c^D \le l_c, \qquad \forall c \text{ served by drone}.
\tag{51}
\end{equation}

In Eq. (18), \(a_c^D\) is drone arrival time at customer \(c\), and \(l_c\) is the latest time of customer \(c\).

Satisfaction is declared when every drone-served customer is reached no later than its latest time. A violation occurs when any drone arrival exceeds the latest bound; in that case, the candidate fails the full hard-feasibility layer. In contrast, the ALNS pre-check omits this condition intentionally and lets the soft objective penalty handle temporal deterioration during search.

The output of this step is one layer-specific temporal-feasibility judgment for drone-served customers.

Code location. src/spd/core.py::check_sortie_feasibility, called by src/spd/core.py::all_hard_constraints_satisfied.

Step 5: Truck load at recovery constraint F5.

This step is performed because truck-drone interaction changes truck load at the recovery event. The truck load at recovery must therefore be checked explicitly, since a sortie can return payload-related consequences to the truck state.

\begin{equation}
\ell_{\mathrm{rec}}^T \le Q_T.
\tag{52}
\end{equation}

In Eq. (19), \(\ell_{\mathrm{rec}}^T\) is truck load at the recovery node, and \(Q_T\) is truck capacity (params.vehicle.truck_capacity).

Satisfaction is declared when the truck load at recovery does not exceed capacity. A violation occurs when the load becomes larger than \(Q_T\); in that case, the candidate is rejected by both the hard-feasibility layer and the structural-and-physical pre-check.

The output of this step is a synchronized payload-feasibility verdict at the drone recovery point.

Code location. src/spd/core.py::check_sortie_feasibility and src/spd/aco_alns.py::_structural_and_physical_check; both are ultimately called by src/spd/aco_alns.py::ALNSOptimizer.optimize.

Step 6: Truck customer time-window constraint F6.

This step is performed because the truck backbone itself must satisfy customer latest times when evaluated under the strict feasibility layer. Even if ALNS allows temporary time-window deterioration through objective penalties, the final best solution must satisfy this route-level requirement.

\begin{equation}
a_c^T \le l_c, \qquad \forall c \text{ served on truck route}.
\tag{53}
\end{equation}

In Eq. (20), \(a_c^T\) is truck arrival time at customer \(c\), and \(l_c\) is its latest time.

Satisfaction is declared when every truck-served customer is reached before or at its latest bound. A violation occurs when a truck arrival exceeds \(l_c\); in that case, the full hard-feasibility layer rejects the candidate, whereas the ALNS pre-check intentionally omits the condition so that soft tardiness can be explored before final best-solution gating.

The output of this step is the strict route-level temporal-feasibility result for truck service.

Code location. src/spd/core.py::is_truck_route_feasible, called by src/spd/core.py::all_hard_constraints_satisfied.

Step 7: Truck route load constraint F7.

This step is performed because pickup and delivery operations modify truck load over the full route, not only at sortie interactions. The full truck load profile must therefore remain capacity-feasible at every route node.

\begin{equation}
\ell_n^T \le Q_T, \qquad \forall n \in \text{truck route}.
\tag{54}
\end{equation}

In Eq. (21), \(\ell_n^T\) is truck load at route node \(n\), and \(Q_T\) is truck capacity.

Satisfaction is declared when the truck load never exceeds capacity at any node. A violation occurs when any node load exceeds \(Q_T\); in that case, the candidate is rejected by both hard feasibility and the structural-and-physical pre-check.

The output of this step is the route-wide truck payload-feasibility result.

Code location. src/spd/core.py::is_truck_route_feasible and src/spd/aco_alns.py::_structural_and_physical_check, both driven by src/spd/core.py::compute_truck_load.

Step 8: Depot return-time constraint F8.

This step is performed because the offline plan must conclude within the depot operating horizon. A route that serves all customers but returns too late cannot be considered strictly feasible.

\begin{equation}
a_{\mathrm{depot\_return}}^T \le L_0.
\tag{55}
\end{equation}

In Eq. (22), \(a_{\mathrm{depot\_return}}^T\) is final truck return time to the depot, and \(L_0\) is depot latest time (params.time.depot_latest).

Satisfaction is declared when the truck returns before or at the depot latest time. A violation occurs when the route ends too late; in that case, the candidate fails the full hard-feasibility layer. The ALNS pre-check omits this condition intentionally, treating it as a soft-search issue handled by objective penalties until final selection.

The output of this step is the strict route-horizon feasibility judgment for final depot return.

Code location. src/spd/core.py::is_truck_route_feasible, called by src/spd/core.py::all_hard_constraints_satisfied.

Step 9: Sortie structural consistency constraint.

This step is performed because a sortie must remain anchored to a valid truck route and must preserve non-overlapping launch-recovery structure. Without such structural checking, destroy-repair operations could produce formally stored but operationally meaningless sortie objects.

\begin{equation}
\text{launch}_s \neq 0,\quad \text{recovery}_s \neq 0,\quad
\text{launch}_s \prec \text{recovery}_s,\quad
\mathcal{C}_s \cap \mathcal{R}_T = \varnothing.
\tag{56}
\end{equation}

In Eq. (23), \(\text{launch}_s\) and \(\text{recovery}_s\) denote the launch and recovery nodes of sortie \(s\), \(\prec\) denotes order on the truck route, \(\mathcal{C}_s\) is the set of sortie customers, and \(\mathcal{R}_T\) is the set of truck-route nodes.

Satisfaction is declared when the sortie anchors are non-depot truck nodes, the launch appears before recovery, and sortie customers do not remain on the truck route. A violation occurs when anchors disappear, order reverses, or adjacent sorties overlap; in that case, the candidate is marked as structurally damaged, and the ALNS loop may trigger fallback rebuild before any SA comparison is attempted.

The output of this step is a structural-validity verdict for the truck-drone coupling pattern.

3.5 ACO Outer Construction and Pheromone Learning Mechanism

The ACO component is introduced because the offline search space is too large for one-shot deterministic construction alone. By learning over directed truck arcs, the outer loop can preserve promising structural regularities while still allowing multiple ants to build diverse route candidates. This choice differs from pure random restart because it accumulates experience across outer iterations through pheromone memory.

The role of one ant is not to produce the final answer directly. Instead, each ant constructs a complete candidate route structure under the current pheromone and heuristic state; subsequently, ALNS refines that candidate locally. As a result, the constructive responsibility is delegated to ACO, whereas local exploitation is delegated to ALNS. The refined ant outcome rather than the raw constructive route is what eventually competes for iteration-best and global-best status.

The relevant ACO parameters are exposed in ACOParameters. The outer iteration cap is max_iterations, the population size per outer iteration is ant_count, the pheromone exponent is alpha_aco, the heuristic exponent is beta_aco, the evaporation rate is evaporation_rate, the deposit strength is pheromone_q, the initial pheromone value is pheromone_init, the no-improvement early-stop threshold is no_improve_max, and the global-best deposit weight is global_best_weight. In the config_small reference file, these values are 20, 5, 1.0, 2.0, 0.2, 10.0, 1.0, 15, and 0.65, respectively.

At the outer-loop level, the algorithm first initializes an all-home starting solution and its objective, then initializes the pheromone dictionary, then repeatedly launches one ant task per ant index. Once the ant outcomes have been collected, the best refined ant is used to update the global incumbent, the pheromone matrix, and the dynamic \(\beta\) schedule. Consequently, the outer shell alternates between constructive diversification and reinforced memory update.

Step 1: Pheromone matrix definition and physical meaning.

This step is performed because the outer search must remember which directed truck arcs have repeatedly appeared in high-quality refined solutions. The learning object is therefore not an entire route chromosome but a directed edge memory over truck arcs.

Let \(\tau_{ij}\) denote pheromone on directed truck arc \((i,j)\). Once this matrix has been defined, the constructive procedure can subsequently bias route extension toward arcs that have historically appeared in iteration-best or global-best solutions.

\begin{equation}
\tau_{ij} \in \mathbb{R}_{>0}, \qquad
\tau_{ij} \text{ stores learned desirability of directed truck arc } (i,j).
\tag{57}
\end{equation}

In Eq. (24), \(i\) and \(j\) are nodes in the truck network. In code, the matrix is represented by the dictionary ACOState.pheromone: dict[tuple[int,int], float].

Satisfaction is declared when every relevant arc used by the constructive process can be queried from the pheromone dictionary, with fallback seeding available for missing edges. A violation occurs when an arc is absent from the dictionary; in that case, the implementation seeds it with an initial pheromone value before deposition.

The output of this step is a directed arc-memory state that can be queried by each ant during route construction.

Code location. src/spd/aco_alns.py::ACOState and src/spd/aco_alns.py::ACOALNSSolver.solve, called by src/spd/main.py::SPDPlanner.solve_offline.

Step 2: Pheromone initialization rule.

This operation is performed because every arc must start from a positive, non-degenerate value before learning begins. Without positive initialization, the multiplicative transition rule would suppress exploration on unseen arcs.

The implementation initializes all directed truck arcs to the same scalar \(\tau_0\). If a distance dictionary is unavailable, the initialization is widened to the full depot-customer Cartesian node set. Once this homogeneous initialization has been completed, route bias emerges only after iteration-best and global-best deposition starts to differentiate edges.

\begin{equation}
\tau_{ij}^{(0)} = \tau_0, \qquad \forall (i,j)\in \mathcal{A}_T.
\tag{58}
\end{equation}

In Eq. (25), \(\tau_0\) is the configured initial pheromone value (params.aco.pheromone_init), which is 1.0 in config_small. In the main ACO solver, this initialization is performed inline rather than by a separate dedicated initializer function.

Satisfaction is declared when all arcs in the active truck distance dictionary receive positive initial pheromone. A violation occurs when the distance dictionary is empty; in that case, the solver creates a dense fallback arc set over all nodes and still assigns \(\tau_0\).

The output of this step is a dense positive pheromone dictionary ready for ant sampling.

Code location. src/spd/aco_alns.py::ACOALNSSolver.solve, called by src/spd/main.py::SPDPlanner.solve_offline. A separate initializer exists only in src/spd/aco_alns.py::PureACOOptimizer._initialize_pheromone, which is outside the present mixed ACO-ALNS path.

Step 3: Pheromone lower and upper bounds.

This step is performed because unbounded pheromone growth or collapse would either freeze the search prematurely or erase learned distinctions almost completely. The implementation therefore imposes an MMAS-style clipping regime.

When explicit bounds are not provided in configuration, the lower bound is set to one-tenth of the initial pheromone and the upper bound is set to ten times the initial pheromone, subject to numerical safety adjustments. Once these bounds have been resolved, every evaporation and deposition update is clipped accordingly.

\begin{equation}
\tau_{\min} = \max(10^{-9}, 0.1\tau_0), \qquad
\tau_{\max} = \max(\tau_{\min}+10^{-9}, 10\tau_0).
\tag{59}
\end{equation}

In Eq. (26), \(\tau_0\) is the initial pheromone value. If params.aco.tau_min and params.aco.tau_max are explicitly set, those values override the derived defaults after legality checks. In config_small, the configured values are \(\tau_{\min}=0.1\) and \(\tau_{\max}=10.0\).

Satisfaction is declared when the resolved bounds satisfy \(\tau_{\max}>\tau_{\min}>0\). A violation occurs when configured values are missing or numerically invalid; in that case, the code derives legal replacements from \(\tau_0\).

The output of this step is a valid clipping interval for all subsequent pheromone updates.

Code location. src/spd/aco_alns.py::ACOALNSSolver._resolve_tau_bounds, called by src/spd/aco_alns.py::ACOALNSSolver.update_pheromone and src/spd/aco_alns.py::ACOALNSSolver.solve.

Step 4: Restricted candidate list construction.

This step is performed because evaluating all unvisited customers at every extension step would reduce constructive efficiency and weaken the intended neighborhood focus of the ant search. The algorithm therefore begins from a restricted near-candidate list ranked by truck distance from the current node.

The remaining customers are first sorted by the truck distance instance.truck_distance_km[(current, candidate)]. Subsequently, the first \(k\) candidates are retained as the near list, where \(k\) is either the configured candidate_list_size or a dynamic value derived from the remaining customer count. In turn, the algorithm uses this near list as the first evaluation pool for transition statistics and feasibility screening.

\begin{equation}
k =
\min\!\left(
|\mathcal{N}_{\mathrm{rem}}|,
\max\!\left(1,\ \left\lfloor \min\!\left(25,\max\!\left(10,4\sqrt{|\mathcal{N}_{\mathrm{rem}}|}\right)\right)\right\rceil \right)
\right),
\tag{60}
\end{equation}

In Eq. (27), \(|\mathcal{N}_{\mathrm{rem}}|\) is the number of remaining customers. This formula applies only when params.aco.candidate_list_size is absent; otherwise, the configured value is used directly. In config_small, the configured value is 10.

Satisfaction is declared when the near list contains at least one candidate to evaluate. A violation occurs when the restricted list contains no feasible transition after screening; in that case, the algorithm explicitly expands the search neighborhood to the full sorted candidate set. If the expanded neighborhood still yields no feasible customer, the implementation falls back to roulette sampling over the available pool using cached weights rather than aborting construction immediately.

The output of this step is a restricted candidate pool that biases the ant toward local promising moves while preserving a controlled expansion path.

Code location. src/spd/aco_alns.py::ACOALNSSolver._resolve_candidate_list_size and src/spd/aco_alns.py::ACOALNSSolver.construct_ant_solution, called by src/spd/aco_alns.py::_run_single_ant.

Step 5: Heuristic value \(\eta_{ij}\) computation.

This operation is performed because pheromone alone cannot encode the immediate geometric and resource consequences of choosing the next customer. The heuristic term therefore summarizes instantaneous attractiveness through one distance component, one time-window-slack component, and one truck-capacity-slack component.

The algorithm first computes the truck distance from the current node to candidate \(j\), then derives the projected arrival time and the projected truck load after servicing \(j\). Subsequently, three normalized sub-terms are formed. The distance term rewards shorter truck moves relative to the average local distance scale; the time-window term rewards larger residual slack before the candidate latest time; and the capacity term rewards larger residual truck capacity after the candidate service action. Once these three quantities have been computed, they are linearly combined using configured weights and lower-bounded numerically by \(10^{-9}\).

\begin{equation}
\eta_{ij}
=
\max\!\left(
10^{-9},
w_{\mathrm{dist}}\eta^{\mathrm{dist}}_{ij}
+
w_{\mathrm{tw}}\eta^{\mathrm{tw}}_{ij}
+
w_{\mathrm{cap}}\eta^{\mathrm{cap}}_{ij}
\right).
\tag{61}
\end{equation}

\begin{equation}
\eta^{\mathrm{dist}}_{ij} =
\frac{1}{1+d_{ij}/\bar d}.
\tag{62}
\end{equation}

\begin{equation}
\eta^{\mathrm{tw}}_{ij} =
\mathrm{clip}_{[0,1]}
\left(
\frac{l_j-a_j}{T_h}
\right).
\tag{63}
\end{equation}

\begin{equation}
\eta^{\mathrm{cap}}_{ij} =
\mathrm{clip}_{[0,1]}
\left(
\frac{Q_T-\hat \ell_j}{Q_T}
\right).
\tag{64}
\end{equation}

In Eqs. (28) to (31), \(d_{ij}\) is truck network distance from the current node to candidate \(j\), \(\bar d\) is the local distance scale dist_scale, \(l_j\) is the latest time of customer \(j\), \(a_j\) is projected arrival time at \(j\), \(T_h\) is the planning horizon length depot_latest - depot_earliest, \(Q_T\) is truck capacity, and \(\hat \ell_j\) is projected truck load after serving \(j\). The weights are w_dist, w_tw, and w_cap. In config_small, these values are 1.0, 1.0, and 0.8, respectively, whereas the code-level fallback defaults inside the constructor are 1.0, 0.8, and 0.6 if configuration is absent.

Satisfaction is declared when all three sub-terms can be computed from valid distance, arrival, and projected-load states. A violation occurs when a transition cannot satisfy the nonnegative slack conditions \(l_j-a_j \ge 0\) and \(Q_T-\hat\ell_j \ge 0\); in that case, the candidate is marked infeasible for the current restricted screening stage, although it may still be reconsidered under the expanded neighborhood fallback logic.

The output of this step is a strictly positive heuristic attractiveness value \(\eta_{ij}\) for each evaluated candidate transition.

Code location. src/spd/aco_alns.py::ACOALNSSolver.construct_ant_solution, inner helper transition_stats, called by src/spd/aco_alns.py::_run_single_ant.

Step 6: Transition weight and roulette-wheel sampling.

This step is performed because the ant must convert pheromone memory and heuristic attractiveness into one actionable stochastic choice. The implementation deliberately uses pure probability-based roulette selection rather than an ACS-style pseudo-random proportional rule with a separate greedy parameter \(q_0\).

The transition weight is computed multiplicatively, after which the algorithm samples one next customer by cumulative roulette probability over the selected pool. Once the draw has been completed, the chosen customer is appended to the route, removed from the remaining set, and used to update the current time and load states. Consequently, the constructive process remains stochastic at every extension step even when some candidates are strongly favored.

\begin{equation}
w_{ij} = \tau_{ij}^{\alpha_{\mathrm{aco}}}\eta_{ij}^{\beta_{\mathrm{aco}}}.
\tag{65}
\end{equation}

\begin{equation}
\Pr(j \mid i) =
\frac{w_{ij}}{\sum_{h\in \mathcal{C}_i} w_{ih}},
\qquad j \in \mathcal{C}_i.
\tag{66}
\end{equation}

In Eqs. (32) and (33), \(\alpha_{\mathrm{aco}}\) and \(\beta_{\mathrm{aco}}\) are the configured pheromone and heuristic exponents, \(\tau_{ij}\) is pheromone on arc \((i,j)\), \(\eta_{ij}\) is the composite heuristic value, and \(\mathcal{C}_i\) is the active candidate pool. In config_small, \(\alpha_{\mathrm{aco}}=1.0\) and \(\beta_{\mathrm{aco}}=2.0\).

Satisfaction is declared when the candidate pool is nonempty and the sum of nonnegative weights is strictly positive. A violation occurs when the total weight degenerates to a nonpositive quantity; in that case, the implementation falls back to uniform random choice over the candidate list rather than terminating. No \(q_0\) parameter was found in the code, so no deterministic-greedy branch exists in the implemented roulette mechanism.

The output of this step is one sampled next customer and an updated partial route state.

Code location. src/spd/aco_alns.py::ACOALNSSolver.construct_ant_solution, inner helper roulette_select, called by src/spd/aco_alns.py::_run_single_ant.

Step 7: Fallback to ETPRC after constructive degradation.

This operation is performed because ant construction may yield a route that becomes unusable once sortie extraction is attempted, or a full candidate that still leaves customers unserved. Rather than discarding the entire ant iteration immediately, the implementation reuses the more robust ETPRC construction path to restore a complete candidate.

Two trigger conditions are implemented. First, if sortie extraction from the ant route raises an exception, the route is rebuilt by ETPRC's deterministic truck-route constructor and reprocessed by sortie extraction. Second, once all groups have been assembled into one candidate solution, the algorithm checks whether unserved_customers is nonempty. If so, the entire candidate is replaced by ETPRCBuilder.build_initial_solution. Consequently, fallback is not driven by a soft quality threshold but by explicit constructive failure conditions.

\begin{equation}
\text{fallback is triggered if }
\left[
\text{sortie extraction fails}
\right]
\ \lor\
\left[
|\mathcal{N}_{\mathrm{unserved}}| > 0
\right].
\tag{67}
\end{equation}

In Eq. (34), \(\mathcal{N}_{\mathrm{unserved}}\) is the set of unserved customers in the constructed ant solution. No code variable corresponding to a predefined “allocation quality threshold” was found in the implementation.

Satisfaction is declared when the constructed ant solution supports valid sortie extraction and covers all customers. A violation occurs under either trigger in Eq. (34); in that case, the algorithm replaces the degraded construction with the ETPRC route-building path or with the full ETPRC initial-solution generator, respectively.

The output of this step is a restored complete candidate whose structural quality is expected to be more stable than the failed ant construction it replaces.

Code location. src/spd/aco_alns.py::ACOALNSSolver.construct_ant_solution, called by src/spd/aco_alns.py::_run_single_ant; fallback constructors are src/spd/etprc.py::ETPRCBuilder._build_truck_route, src/spd/etprc.py::ETPRCBuilder._extract_sorties, and src/spd/etprc.py::ETPRCBuilder.build_initial_solution.

Step 8: Global evaporation.

This step is performed because pheromone values must decay over time if they are not continually reinforced by good solutions. Without evaporation, early historical bias would dominate later search excessively and diversity would collapse.

At the end of each outer iteration, the solver traverses the entire pheromone dictionary and multiplies every value by \((1-\rho)\). Subsequently, each value is clipped to the legal interval \([\tau_{\min},\tau_{\max}]\), thereby coupling evaporation with bounded memory preservation.

\begin{equation}
\tau_{ij} \leftarrow
\mathrm{clip}\!\left((1-\rho)\tau_{ij},\tau_{\min},\tau_{\max}\right).
\tag{68}
\end{equation}

In Eq. (35), \(\rho\) is the evaporation rate (params.aco.evaporation_rate), which is 0.2 in config_small.

Satisfaction is declared when every pheromone value remains strictly within the legal clipping interval after evaporation. A violation occurs when raw evaporation would reduce a value below the lower bound or when numerical inconsistency arises; in that case, clipping restores legality.

The output of this step is a globally decayed pheromone field whose stale biases have been weakened.

Code location. src/spd/aco_alns.py::ACOALNSSolver.update_pheromone, called by src/spd/aco_alns.py::ACOALNSSolver.solve.

Step 9: Iteration-best pheromone deposition.

This step is performed because the best refined ant in the current outer iteration contains the most recent locally improved structural information. Reinforcing its truck arcs allows the next ACO iteration to benefit from current constructive evidence rather than only from historical incumbents.

The deposition amount is inversely proportional to the current best objective value, so that better solutions contribute larger reinforcement. Deposition is applied only on truck edges contained in the iteration-best solution, rather than on all ants or on drone-specific edges. Consequently, the pheromone learning object remains aligned with the truck-arc constructive layer.

\begin{equation}
\Delta \tau_{\mathrm{iter}}
=
\frac{Q_{\mathrm{aco}}}{Z_{\mathrm{iter}}}.
\tag{69}
\end{equation}

\begin{equation}
\tau_{ij} \leftarrow
\mathrm{clip}\!\left(\tau_{ij}+\Delta \tau_{\mathrm{iter}},\tau_{\min},\tau_{\max}\right),
\qquad (i,j)\in \mathcal{E}_{\mathrm{iter}}.
\tag{70}
\end{equation}

In Eqs. (36) and (37), \(Q_{\mathrm{aco}}\) is the pheromone deposit strength (params.aco.pheromone_q), \(Z_{\mathrm{iter}}\) is the objective of the iteration-best solution, and \(\mathcal{E}_{\mathrm{iter}}\) is the set of truck edges extracted from that solution.

Satisfaction is declared when a valid iteration-best solution and positive objective value are available. A violation occurs when iteration-best is absent or its objective is nonpositive; in that case, the deposit step is skipped safely.

The output of this step is a current-iteration reinforcement on arcs used by the best refined ant of the present outer cycle.

Code location. src/spd/aco_alns.py::ACOALNSSolver.update_pheromone, inner helper _deposit, called by src/spd/aco_alns.py::ACOALNSSolver.solve.

Step 10: Global-best weighted deposition and clipping analysis.

This step is performed because the search should preserve memory of the strongest incumbent even when the current iteration-best is noisy. A weighted global-best deposit therefore stabilizes the search trajectory by continuously reinforcing historically dominant arcs.

The deposit magnitude is again inversely proportional to the global-best objective, but it is multiplied by \(\omega_g\), which controls the strength of historical reinforcement. Once this weighted deposit has been applied, all touched pheromone values are clipped back into the legal interval. This final clipping is required because the combined iteration-best and global-best reinforcement could otherwise produce pheromone saturation and excessive constructive determinism.

\begin{equation}
\Delta \tau_{\mathrm{global}}
=
\omega_g \frac{Q_{\mathrm{aco}}}{Z_{\mathrm{global}}}.
\tag{71}
\end{equation}

\begin{equation}
\tau_{ij} \leftarrow
\mathrm{clip}\!\left(\tau_{ij}+\Delta \tau_{\mathrm{global}},\tau_{\min},\tau_{\max}\right),
\qquad (i,j)\in \mathcal{E}_{\mathrm{global}}.
\tag{72}
\end{equation}

In Eqs. (38) and (39), \(\omega_g\) is the global-best weight (params.aco.global_best_weight), which is 0.65 in config_small, \(Z_{\mathrm{global}}\) is the objective of the global-best refined solution, and \(\mathcal{E}_{\mathrm{global}}\) is its truck-edge set.

Satisfaction is declared when a valid global-best solution exists and clipping preserves bounded pheromone diversity. A violation occurs when no valid global-best is available; in that case, the global deposit is skipped. The output of this step is a bounded dual-source pheromone update that combines recency and long-term memory. Relative to standard AS, the implementation does not deposit from all ants; relative to ACS, it has no local online update and no \(q_0\) rule; relative to MMAS, it shares the bounded pheromone philosophy but uses a mixed iteration-best plus weighted global-best deposition sequence.

Code location. src/spd/aco_alns.py::ACOALNSSolver.update_pheromone, called by src/spd/aco_alns.py::ACOALNSSolver.solve.

3.6 ALNS Local Improvement Mechanism

The ALNS layer is introduced because one ant construction, even when pheromone-guided, is still structurally myopic. ALNS therefore acts as a local improver attached to each ant rather than as an independent outer optimizer. Consequently, every refined ant solution already carries local search information before it participates in pheromone learning.

Information flows from ACO to ALNS through the ant-constructed initial candidate and the current global-best objective reference. Information flows back from ALNS to ACO indirectly rather than by direct pheromone manipulation: the refined solution returned by ALNS is what competes for iteration-best and global-best status, and only that refined solution is later used by the ACO pheromone updater. The local search result thus influences pheromone memory through solution quality rather than through direct side effects on the pheromone state.

Step 1: Initialization of current solution, local best, temperature, and operator weights.

This step is performed because ALNS requires an accepted current state for exploration, a best feasible reference for return, a temperature for simulated annealing, and adaptive weights for operator selection. These search states must be defined before the first destroy-repair move can be evaluated.

The implementation deep-copies the incoming ant solution into the current state, evaluates its objective under the initial \(\beta\), and duplicates it again as the local best reference. Subsequently, all destroy and repair operator weights are initialized to the same positive value, and the SA temperature is initialized from configuration. As a result, the inner loop starts from a feasible constructive seed with neutral operator preferences.

\begin{equation}
w_d^{(0)} = w_r^{(0)} = w_0, \qquad
T^{(0)} = T_0.
\tag{73}
\end{equation}

In Eq. (40), \(w_0\) is params.alns.operator_weight_init, and \(T_0\) is params.alns.sa_initial_temperature. In config_small, these values are 1.0 and 100.0.

Satisfaction is declared when the input solution admits valid objective evaluation and all operator lists are nonempty. A violation occurs when no destroy or no repair operator exists; in that case, the optimizer immediately returns a deep copy of the initial solution.

The output of this step is a fully initialized ALNS search state \((S_{\mathrm{cur}}, S_{\mathrm{best}}, T, \mathbf{w}_D, \mathbf{w}_R)\).

Code location. src/spd/aco_alns.py::ALNSOptimizer.optimize, called by src/spd/aco_alns.py::_run_single_ant.

Step 2: Operator selection by roulette-wheel weighting.

This step is performed because the algorithm must balance operator diversity against learned operator quality. A deterministic always-best operator choice would collapse exploration prematurely, whereas fixed random selection would ignore performance feedback.

The current destroy weight vector and repair weight vector are each passed into a roulette-wheel selector. Subsequently, one destroy index and one repair index are sampled independently. Once these two selections have been completed, one destroy-repair pair becomes responsible for generating the next candidate move.

\begin{equation}
\Pr(D_i)=\frac{w_{D_i}}{\sum_h w_{D_h}}, \qquad
\Pr(R_j)=\frac{w_{R_j}}{\sum_h w_{R_h}}.
\tag{74}
\end{equation}

In Eq. (41), \(w_{D_i}\) and \(w_{R_j}\) are the current adaptive weights of destroy operator \(i\) and repair operator \(j\). The implementation uses a cumulative-probability roulette selector with a fallback to a random index if the total positive weight collapses.

Satisfaction is declared when at least one positive or nonnegative weight is available in each operator family. A violation occurs when the total becomes nonpositive; in that case, the selector falls back to uniform random index selection over the operator list.

The output of this step is one selected destroy operator, one selected repair operator, and their indices for later adaptive update.

Code location. src/spd/aco_alns.py::ALNSOptimizer.optimize, inner helper roulette_select, called within the ALNS loop itself.

Step 3: Destruction by sampled removal cardinality.

This step is performed because the search must temporarily release customers from their current assignment before alternative structural patterns can be explored. The removal cardinality is randomized so that local search does not become trapped in one fixed perturbation scale.

The implementation first resolves the lower and upper removal bounds, then samples one integer removal size uniformly from that interval. Subsequently, the selected destroy operator removes that many customers from the current solution and produces a partial solution together with the removed-customer list. As a result, the candidate neighborhood scale varies across ALNS iterations.

\begin{equation}
q \sim \mathcal{U}\{q_{\min}, q_{\max}\}.
\tag{75}
\end{equation}

In Eq. (42), \(q_{\min}\) and \(q_{\max}\) are params.alns.remove_count_min and params.alns.remove_count_max. In config_small, these values are 1 and 3.

Satisfaction is declared when the sampled cardinality can be clamped legally into the customer-set size. A violation occurs when the requested removal count exceeds the number of customers; in that case, the destroy operators normalize it by bounded clamping.

The output of this step is one partial solution and one removed-customer list for repair.

Code location. src/spd/aco_alns.py::ALNSOptimizer.optimize for cardinality sampling, and src/spd/aco_alns.py::_normalized_remove_count plus the concrete destroy operators, called by the ALNS loop.

Step 4: Repair by feasible reinsertion.

This step is performed because the removed customers must be reassigned to restore candidate completeness or at least approach it. The repair operators differ in their ranking logic, yet they all rely on the same candidate-enumeration engine that evaluates feasible truck insertion, insertion into an existing sortie, or creation of a new sortie.

The repair operator receives the partial solution and the removed-customer list, generates candidate reinsertion states under hard-feasibility filtering, and chooses one sequence of insertions according to its internal policy. Once this process has been completed, the algorithm obtains a repaired candidate that is ready for structural damage diagnosis and possible fallback rebuild.

\begin{equation}
\mathcal{C}(c)=
\left\{
S' \mid
S' \text{ is a feasible reinsertion state for removed customer } c
\right\}.
\tag{76}
\end{equation}

In Eq. (43), \(\mathcal{C}(c)\) denotes the set of feasible reinsertion candidates for customer \(c\), generated by the shared helper _candidate_solutions_for_customer.

Satisfaction is declared when at least one feasible reinsertion state exists for the current repair decision. A violation occurs when no reinsertion candidate can be generated; in that case, the operator either defers the customer, breaks, or returns a partially restored candidate that will later be processed by fallback rebuild.

The output of this step is one repaired candidate solution with updated route-sortie structure.

Code location. src/spd/aco_alns.py::_candidate_solutions_for_customer, called by src/spd/aco_alns.py::r1_greedy_insertion, src/spd/aco_alns.py::r2_regret_insertion, and src/spd/aco_alns.py::r3_timeslot_aware_insertion.

Step 5: Fallback rebuild after unserved or damaged structure.

This step is performed because destroy-repair can produce a candidate in which some customers remain unserved or the sortie structure becomes invalid, for example when launch or recovery anchors disappear from the truck route. Instead of discarding such a candidate immediately, the implementation first attempts a structured recovery by rebuilding affected pairs with ETPRC primitives.

The optimizer checks two triggers: whether new_solution.unserved_customers is nonempty and whether any pair satisfies _needs_sortie_rebuild(pair). If either condition holds, _fallback_rebuild is executed in place. That procedure first identifies damaged pairs, then assigns any unserved customer to the nearest pair by average geometric proximity, and subsequently rebuilds affected pairs through _build_truck_route and _extract_sorties. If rebuilding still leaves a structurally invalid sortie pattern, the procedure clears sorties and pushes affected customers back to truck service. Consequently, fallback is a constructive repair hierarchy rather than a trivial rollback.

\begin{equation}
\text{fallback trigger} =
\left[
|\mathcal{N}_{\mathrm{unserved}}|>0
\right]
\lor
\left[
\exists p:\ \mathrm{damaged}(p)=1
\right].
\tag{77}
\end{equation}

In Eq. (44), \(\mathrm{damaged}(p)\) denotes the Boolean result of _needs_sortie_rebuild for pair \(p\).

Satisfaction is declared when fallback rebuild returns a structurally coherent candidate with recomputed served and unserved sets. A violation occurs when rebuilt pairs still cannot maintain valid sortie structure; in that case, the implementation downgrades the affected pair by clearing sorties and moving those customers back to the truck route. Importantly, the fallback result is not discarded automatically. Instead, the fallback-rebuilt candidate continues to the next feasibility layer and therefore can still participate in SA comparison if it passes the subsequent pre-check.

The output of this step is one fallback-processed candidate solution whose structural damage has either been repaired or downgraded into a truck-only form.

Code location. src/spd/aco_alns.py::_fallback_rebuild, called by src/spd/aco_alns.py::ALNSOptimizer.optimize; supporting helpers are src/spd/aco_alns.py::_needs_sortie_rebuild, src/spd/etprc.py::ETPRCBuilder._build_truck_route, and src/spd/etprc.py::ETPRCBuilder._extract_sorties.

Step 6: Periodic cross-group perturbation.

This step is performed because standard destroy-repair may remain trapped inside one pair-local neighborhood for many iterations. A low-frequency cross-group operator is therefore injected to exchange or transfer customers across vehicle pairs and thereby enlarge the reachable search region.

The ALNS loop checks whether cross-group operators are available, whether the configured frequency is positive, and whether the current iteration index satisfies the periodic trigger condition. Once all three conditions have been met, one cross-group operator is selected uniformly at random and applied to the current candidate. As a result, the search occasionally explores inter-pair rearrangements that are not easily produced by within-pair repair alone.

\begin{equation}
\text{cross-group trigger at iteration } t
\iff
F_{\mathrm{cross}} > 0
\ \land\
t \bmod F_{\mathrm{cross}} = 0.
\tag{78}
\end{equation}

In Eq. (45), \(F_{\mathrm{cross}}\) is params.alns.cross_group_frequency, which is 10 in config_small.

Satisfaction is declared when the periodic trigger holds and at least one cross-group operator exists. A violation occurs when the trigger does not fire or the operator list is empty; in that case, no cross-group perturbation is applied in that iteration.

The output of this step is either the unchanged candidate or one inter-pair perturbed candidate ready for feasibility screening.

Code location. src/spd/aco_alns.py::ALNSOptimizer.optimize, calling src/spd/aco_alns.py::cross_pair_swap or src/spd/aco_alns.py::cross_pair_transfer.

Step 7: Structural-and-physical pre-check.

This step is performed because the ALNS loop should reject obviously broken or physically impossible candidates before paying the cost of full objective evaluation. At the same time, the search should remain tolerant of temporary time-window degradation so that soft-penalty exploration remains possible.

The pre-check therefore verifies timeline computability, sortie structure, sortie sequence, sortie cardinality, drone energy, drone payload, truck load at recovery, and truck load along the route. In turn, it intentionally skips the drone-customer time-window bound, the truck-customer time-window bound, and the depot-return bound, because these are handled as soft-search phenomena through the objective and later strict best-solution gating. Consequently, the pre-check is neither a full hard-feasibility oracle nor a purely structural validator; it is an intermediate feasibility layer.

\begin{equation}
\mathcal{F}_{\mathrm{pre}}
=
\{\text{timeline},\text{structure},\text{sequence},F1,F2,F5,F7\}.
\tag{79}
\end{equation}

In Eq. (46), \(\mathcal{F}_{\mathrm{pre}}\) denotes the set of checks enforced by _structural_and_physical_check. The omitted soft-penalty set is \(\{F4,F6,F8\}\).

Satisfaction is declared when all checks in \(\mathcal{F}_{\mathrm{pre}}\) pass. A violation occurs when any one of these checks fails; in that case, the candidate is skipped immediately, receives zero reward, does not enter SA comparison, and only contributes one history row as an invalid move.

The output of this step is a binary pre-screening decision that determines whether the candidate can proceed to objective comparison.

Code location. src/spd/aco_alns.py::_structural_and_physical_check, called by src/spd/aco_alns.py::ALNSOptimizer.optimize.

Step 8: Objective evaluation and SA acceptance.

This step is performed because a structurally and physically admissible candidate must still be compared against the current accepted state under a controlled exploration rule. The algorithm therefore computes the objective under the current \(\beta\) and applies simulated annealing acceptance.

The candidate objective is first computed. Subsequently, the difference \(\Delta = Z_{\mathrm{new}}-Z_{\mathrm{cur}}\) is formed. If \(\Delta<0\), the candidate is accepted deterministically. Otherwise, the candidate is accepted probabilistically according to the Metropolis rule. Once this decision has been completed, the algorithm can in turn assign one reward class and update the current state if acceptance occurs.

\begin{equation}
\Delta = Z_{\mathrm{new}}-Z_{\mathrm{cur}}.
\tag{80}
\end{equation}

\begin{equation}
P_{\mathrm{acc}} =
\begin{cases}
1, & \Delta < 0,\\
\exp(-\Delta/T), & \Delta \ge 0.
\end{cases}
\tag{81}
\end{equation}

In Eqs. (47) and (48), \(Z_{\mathrm{new}}\) and \(Z_{\mathrm{cur}}\) are the candidate and current objectives, and \(T\) is the current SA temperature.

Satisfaction is declared when the candidate either improves the objective or survives the Metropolis draw. A violation occurs when a non-improving candidate fails the draw; in that case, the current solution remains unchanged, the reward stays at zero, and the search continues from the previous accepted state.

The output of this step is an acceptance decision and, if accepted, a new current solution state for the ALNS search trajectory.

Code location. src/spd/aco_alns.py::ALNSOptimizer.optimize, called by src/spd/aco_alns.py::_run_single_ant.

Step 9: Adaptive weight update and temperature cooling.

This step is performed because operator utility is not known a priori and because SA exploration strength must gradually decrease over time. The algorithm therefore updates only the selected destroy and repair operator weights and then cools the current temperature geometrically.

Once the reward class has been determined, the selected destroy and repair weights are updated by exponential smoothing with reaction factor \(r\). Subsequently, the temperature is multiplied by the cooling rate. As a result, the search gradually reallocates probability toward historically successful operators while simultaneously reducing tolerance for worsening moves.

\begin{equation}
w' = (1-r)w + r \cdot \mathrm{reward}.
\tag{82}
\end{equation}

\begin{equation}
T' = \max(T\alpha_{\mathrm{sa}},10^{-9}).
\tag{83}
\end{equation}

In Eqs. (49) and (50), \(r\) is params.alns.reaction_factor, reward is one of \(\sigma_1,\sigma_2,\sigma_3,0\), and \(\alpha_{\mathrm{sa}}\) is params.alns.sa_cooling_rate.

Satisfaction is declared when updated weights remain numerically positive and temperature remains above the hard lower bound. A violation occurs when invalid candidates produce no reward; in that case, the same update rule still applies with reward \(=0\), causing selected operator weights to decay toward zero while temperature still cools.

The output of this step is a refreshed adaptive operator distribution and a reduced SA exploration temperature.

Code location. src/spd/aco_alns.py::ALNSOptimizer.optimize, called by src/spd/aco_alns.py::_run_single_ant.

Step 10: Best-solution gating by full hard feasibility.

This step is performed because the current accepted state and the best solution returned by ALNS are not allowed to play the same role. A state can be accepted for exploration under SA even if it is not suitable to be returned as the final local best. The implementation therefore introduces a final hard-feasibility gate before updating best_local.

The algorithm checks whether the accepted current objective improves the best-local objective or whether the previous best-local has somehow become infeasible. Subsequently, the candidate is passed to all_hard_constraints_satisfied. Only when full hard feasibility holds is best_local replaced. Consequently, ALNS can explore more broadly than the quality required for its returned solution.

\begin{equation}
S_{\mathrm{best}} \leftarrow S_{\mathrm{cur}}
\iff
\left[
Z_{\mathrm{cur}} < Z_{\mathrm{best}}
\right]
\land
\left[
\mathrm{HardFeasible}(S_{\mathrm{cur}})=1
\right].
\tag{84}
\end{equation}

In Eq. (51), \(\mathrm{HardFeasible}(\cdot)\) denotes the strict feasibility result of all_hard_constraints_satisfied.

Satisfaction is declared when all three feasibility layers are aligned: fallback has repaired any structural break, the structural-and-physical pre-check has passed, and the final hard-feasibility checker confirms strict feasibility. A violation at the fallback layer triggers structured rebuild; a violation at the pre-check layer leads to immediate skip without SA; a violation at the hard-feasible best gate allows the current state to remain accepted for exploration but blocks promotion to local best.

The output of this step is a guaranteed hard-feasible local best returned by the ALNS procedure.

Code location. src/spd/core.py::all_hard_constraints_satisfied, called by src/spd/aco_alns.py::ALNSOptimizer.optimize.

3.7 Neighborhood Operator Design

D1 Random Removal.

This operation is performed because the operator pool requires one purely diversification-oriented perturbation that does not presuppose any structural diagnosis. D1 therefore plays the role of unbiased exploration and complements more informed removers by injecting stochastic perturbation into the search trajectory.

The operator first sorts the current assigned customer set, then clamps the requested removal count into the legal interval \([0,|\mathcal{N}_{\mathrm{assigned}}|]\), and subsequently samples \(q\) customers uniformly without replacement. Once the selected customers have been identified, each one is removed from truck and sortie assignments by the common in-place removal helper, and all removed customers are inserted into the unserved set. Consequently, D1 perturbs the current solution without embedding any objective or probability prior.

\begin{equation}
\mathcal{R}_{D1} \sim \text{UniformSample}\left(\mathcal{N}_{\mathrm{assigned}}, q\right).
\tag{85}
\end{equation}

In Eq. (52), \(\mathcal{R}_{D1}\) is the set of removed customers and \(q\) is the sampled removal cardinality. The randomness source is the Python random generator passed as rng.

Satisfaction is declared when exactly \(q\) distinct customers are removed and none of them remains in truck or drone assignment. A violation occurs when the requested \(q\) exceeds the number of assigned customers; in that case, the count is normalized by clamping before sampling. The output of this step is one partial solution and one removed-customer list for subsequent repair. Code location: src/spd/aco_alns.py::d1_random_removal, called by src/spd/aco_alns.py::ALNSOptimizer.optimize. A figure is recommended here because a before-and-after visualization of randomly removed truck and sortie customers would clarify the operator's exploratory role.

D2 Worst Removal.

This operation is performed because the operator pool also requires one exploitation-oriented destroyer that explicitly attacks customers whose current assignment contributes most strongly to the present objective. D2 therefore serves as the directed counterpart of D1 and focuses the search on the most expensive local assignment decisions.

The operator begins by evaluating the baseline objective of the current complete solution. Subsequently, for each customer \(c\), it constructs a hypothetical candidate in which only \(c\) is removed. The marginal objective relief of customer \(c\) is then defined as the difference between the baseline objective and the single-removal objective. Once these marginal contributions have been computed, customers are sorted deterministically in descending order of relief, and the first \(q\) customers are removed. Ties are broken by ascending customer identifier because the implementation sorts by (-improvement, customer_id). Consequently, D2 is fully deterministic once the current solution is fixed.

\begin{equation}
\Delta_c^{\mathrm{marg}}
=
Z(S) - Z(S \setminus \{c\}).
\tag{86}
\end{equation}

In Eq. (53), \(S\) is the current solution and \(S \setminus \{c\}\) denotes the solution obtained by removing only customer \(c\) from the assignment. The score used for ranking is exactly \(\Delta_c^{\mathrm{marg}}\). No probabilistic ranking is used once the score vector is available.

Satisfaction is declared when all single-customer removal states admit objective evaluation and a ranked list can be formed. A violation occurs when removing one customer produces an invalid candidate that cannot be evaluated; in that case, the implementation assigns \(-\infty\) to the corresponding improvement score, ensuring that such a customer is never selected unless no evaluable alternative exists. The output of this step is a partial solution focused on the presently most burdensome assignments. Code location: src/spd/aco_alns.py::d2_worst_removal, called by src/spd/aco_alns.py::ALNSOptimizer.optimize. This operator is naturally complementary to D1 because D1 explores unstructured perturbation whereas D2 exploits known high-cost structure. A figure is recommended because a bar chart of marginal relief values would make the deterministic top-\(q\) selection transparent.

D3 Related Removal.

This operation is performed because spatially correlated customers often participate in the same local structural defect, such as one poorly arranged cluster on the route or one subregion with weak sortie assignment. D3 therefore introduces geographically coherent perturbation and fills the gap between purely random and purely cost-ranked removal.

The operator first chooses one seed customer uniformly from the currently assigned set. Subsequently, all other assigned customers are ranked by Euclidean distance to the seed, and the nearest \(q-1\) customers are removed together with the seed. Once this removal has been applied, the resulting partial solution encodes a localized hole in the customer geography, which repair can later fill in a structurally different way.

\begin{equation}
d^{\mathrm{geo}}(c,\hat c)
=
\sqrt{(x_c-x_{\hat c})^2 + (y_c-y_{\hat c})^2}.
\tag{87}
\end{equation}

In Eq. (54), \(\hat c\) is the random seed customer and \((x_c,y_c)\) is the geometric coordinate of customer \(c\). The seed choice is stochastic, but conditional on the seed, the remaining ranking is deterministic by geographic proximity.

Satisfaction is declared when the operator returns one seed-centered removal set of legal size. A violation occurs when \(q\) exceeds the number of assigned customers; in that case, bounded normalization still guarantees a legal removal count. The output of this step is one geographically localized partial solution. Code location: src/spd/aco_alns.py::d3_related_removal, called by src/spd/aco_alns.py::ALNSOptimizer.optimize. This operator complements D1 and D2 because it destroys local geographical coherence rather than purely random or purely marginal-cost structure. A figure is recommended because a seed-and-neighborhood scatter plot can explain the operator immediately.

D4 Low Home-Probability Removal.

This operation is performed because the problem includes exogenous customer home-presence uncertainty through slot-wise probability vectors. D4 therefore attacks customers whose current planned arrival slots are least reliable, thereby allowing repair to seek assignments with better expected attendance timing.

The operator first computes the current truck timeline for each pair. Subsequently, for each customer, it retrieves the planned arrival time, maps that time into one bounded time slot by map_time_to_slot, and reads the corresponding probability from customer.home_probabilities. The customers are then sorted in ascending order of that planned-slot probability, and the first \(q\) customers are removed. In the current data model, home_probabilities is a fixed tuple whose length equals the number of time slots, which is params.time.num_time_slots. Consequently, D4 is not a Monte Carlo destroyer. It is a deterministic ranking operator driven by exogenous slot probability data. 

\begin{equation}
\mathrm{score}_{D4}(c)=p_c(t_c^\ast),
\qquad
t_c^\ast = \mathrm{map\_time\_to\_slot}(a_c).
\tag{88}
\end{equation}

In Eq. (55), \(a_c\) is the planned arrival time of customer \(c\), \(t_c^\ast\) is the mapped slot index, and \(p_c(t_c^\ast)\) is the stored home probability in that slot. The slot mapping uses the depot earliest time, depot latest time, and slot length derived from num_time_slots. In config_small, the number of time slots is 8.

Satisfaction is declared when each customer admits a valid timeline arrival and slot probability lookup. A violation occurs when timeline or slot access fails; in that case, the implementation assigns the conservative fallback probability value 1.0 so that the customer is not wrongly prioritized for low-probability removal. The output of this step is one probability-informed partial solution that emphasizes temporal-risk restructuring. Code location: src/spd/aco_alns.py::d4_low_home_probability_removal and src/spd/config.py::map_time_to_slot, called by src/spd/aco_alns.py::ALNSOptimizer.optimize. This operator complements D1, D2, and D3 because it destroys reliability-exposed timing assignments rather than random, spatial, or marginal-cost structure. A figure is recommended because a slot-probability heatmap aligned with planned arrivals would clarify the ranking mechanism.

R1 Greedy Insertion.

This operation is performed because the repair pool requires one direct myopic reinsertion rule that greedily chooses the best currently available feasible insertion. R1 therefore acts as the lowest-overhead intensification operator and supplies a fast local completion mechanism after destruction.

The operator maintains a pending queue of removed customers. For the customer at the queue head, it enumerates all feasible truck insertions, insertions into existing sorties, and insertions through creation of a new sortie. Subsequently, it selects the candidate solution with the smallest objective value and commits that insertion immediately. If no candidate is available, the customer is moved to the back of the queue and retried later. Once no-progress rounds reach the current pending size, the loop stops. Consequently, R1 is greedy in objective value but still allows deferred retry when the current partial structure is temporarily too restrictive.

\begin{equation}
S_{R1}(c)=\arg\min_{S' \in \mathcal{C}(c)} Z(S').
\tag{89}
\end{equation}

In Eq. (56), \(\mathcal{C}(c)\) is the feasible reinsertion set for customer \(c\). The operator uses no additional randomness internally once the candidate set has been generated.

Satisfaction is declared when at least one feasible reinsertion exists for the current queue head. A violation occurs when \(\mathcal{C}(c)=\varnothing\); in that case, the customer is deferred to a later round rather than forcing an infeasible insertion. The output of this step is an incrementally repaired solution that locally minimizes current objective value. Code location: src/spd/aco_alns.py::r1_greedy_insertion, called by src/spd/aco_alns.py::ALNSOptimizer.optimize. This operator complements R2 and R3 because it prioritizes immediate objective minimization over regret sensitivity or slot-probability awareness. A figure is not strictly necessary here because the logic is already transparent from the prose and formula.

R2 Regret Insertion.

This operation is performed because a purely greedy insertion can make an early low-regret decision that blocks a later high-risk customer from any good insertion position. R2 therefore introduces a look-ahead notion by prioritizing customers whose second-best alternative is much worse than their best one.

The operator evaluates feasible insertion candidates for every pending customer. Once those candidate lists have been built, it sorts each list by objective value, reads the best and second-best objectives, and computes the regret value as their difference. Subsequently, it selects the customer with the largest regret and commits that customer's best insertion. The intuition is that a large regret indicates a customer for whom postponement is dangerous, because the loss from not taking the best available position now would be substantial. Consequently, R2 often outperforms R1 in situations where feasible insertion opportunities are scarce and asymmetric across customers.

\begin{equation}
\mathrm{regret}(c)=Z_2(c)-Z_1(c),
\tag{90}
\end{equation}

where \(Z_1(c)\) and \(Z_2(c)\) denote the best and second-best feasible insertion objectives for customer \(c\). A larger regret means that customer \(c\) has one particularly valuable insertion position that should not be postponed.

Satisfaction is declared when at least one customer has a nonempty feasible candidate list. A violation occurs when no pending customer admits any feasible insertion; in that case, the operator terminates and returns the currently repaired solution, leaving further completion to fallback rebuild if needed. The output of this step is one repaired solution biased toward customers with fragile insertion opportunities. Code location: src/spd/aco_alns.py::r2_regret_insertion, called by src/spd/aco_alns.py::ALNSOptimizer.optimize. This operator complements R1 because R1 is purely current-cost greedy whereas R2 explicitly protects customers with high future opportunity loss. A figure is recommended because a best-versus-second-best insertion sketch makes the regret principle immediately understandable.

R3 Timeslot-aware Insertion.

This operation is performed because an insertion with slightly higher current route cost may still be preferable if it moves the customer to a much higher home-probability arrival slot. R3 therefore complements cost-oriented repair by explicitly prioritizing reliability-aware temporal placement.

The operator enumerates feasible insertion candidates exactly as in the shared repair engine. Subsequently, for each candidate it computes the arrival-slot home probability of the inserted customer. The operator then selects the candidate with the highest such probability, using minimum objective value only as a tie-breaker. Consequently, R3 is neither purely greedy nor purely regret-based; it is a targeted repair for probability-sensitive temporal alignment.

\begin{equation}
S_{R3}(c)=
\arg\max_{S' \in \mathcal{C}(c)} p_c(t_c^\ast(S')),
\quad
\text{tie-break by } \arg\min Z(S').
\tag{91}
\end{equation}

In Eq. (58), \(p_c(t_c^\ast(S'))\) is the home probability of customer \(c\) under candidate solution \(S'\) at its induced arrival slot.

Satisfaction is declared when at least one feasible insertion candidate exists for the customer under consideration. A violation occurs when no candidate exists; in that case, the operator simply skips that customer and proceeds. The output of this step is one repaired solution biased toward more reliable arrival slots. Code location: src/spd/aco_alns.py::r3_timeslot_aware_insertion, called by src/spd/aco_alns.py::ALNSOptimizer.optimize. This operator complements R1 and R2 because it explicitly prioritizes attendance probability rather than cost greediness or regret sensitivity. A figure is recommended because one customer placed in three different slots with different probabilities would illustrate the selection rule effectively.

Cross-pair Swap.

This operation is performed because some deficiencies cannot be resolved inside one pair-local neighborhood. Cross-pair swap therefore introduces a low-frequency inter-pair structural move that exchanges customer subsets between two used pairs.

The operator first samples two used vehicle pairs and then samples one small customer subset from each pair, with size determined by cross_group_remove_count. Subsequently, the subsets are exchanged, and the target customer sets of both pairs are rebuilt from scratch through _rebuild_pair. The rebuilt solution is accepted only if it is fully hard-feasible and strictly improves the objective relative to the pre-swap solution. Consequently, cross-pair swap is not governed by SA acceptance and does not participate in the adaptive destroy-repair weight scheme, because it is triggered periodically outside the main weighted operator family and is designed as a conservative strategic perturbation rather than a frequently sampled local move.

\begin{equation}
S' =
\begin{cases}
\text{rebuild}(\text{swap}(S)), & \text{if hard-feasible and } Z(S') < Z(S),\\
S, & \text{otherwise}.
\end{cases}
\tag{92}
\end{equation}

In Eq. (59), \(\text{swap}(S)\) denotes subset exchange between two pair customer sets, and rebuild denotes pair-level reconstruction through ETPRC route and sortie extraction.

Satisfaction is declared when the rebuilt swapped solution is hard-feasible and strictly better than the incumbent. A violation occurs when feasibility fails or the objective does not improve; in that case, the operator deterministically returns the original solution. The output of this step is either the unchanged incumbent or one strictly improved inter-pair solution. Cross-pair Transfer.

This operation is performed because a full subset swap may be unnecessarily strong when only one customer is badly assigned to the wrong pair. Cross-pair transfer therefore provides a lighter inter-pair perturbation by moving one customer from one pair to another.

The operator randomly selects two used pairs, then chooses one customer from the source pair and moves it into the target pair. Subsequently, both pairs are rebuilt through _rebuild_pair, the unserved set is recomputed, and the rebuilt solution is accepted only if it is hard-feasible and strictly improving. Just like swap, this operator is periodic rather than weight-adaptive, and its acceptance is deterministic rather than SA-based, because it is intended as a guarded strategic perturbation that should not inject unstable worsening inter-pair states into the search trajectory.

\begin{equation}
S' =
\begin{cases}
\text{rebuild}(\text{transfer}(S)), & \text{if hard-feasible and } Z(S') < Z(S),\\
S, & \text{otherwise}.
\end{cases}
\tag{93}
\end{equation}

In Eq. (60), \(\text{transfer}(S)\) denotes moving one customer across pairs before rebuilding.

Satisfaction is declared when the transfer-rebuilt candidate is strictly improving and fully hard-feasible. A violation occurs when feasibility fails or no strict improvement is achieved; in that case, the operator returns the original solution. The output of this step is either the unchanged incumbent or one stricter inter-pair improvement than pair-local repair can provide. When the full operator pool is considered jointly, a clear complementarity pattern emerges. D1, D2, D3, and D4 disturb the incumbent along random, marginal-cost, geographic, and attendance-probability dimensions, respectively. In turn, R1, R2, and R3 reconstruct the removed customers through objective greediness, opportunity-loss awareness, and slot-probability awareness. Consequently, the destroy side spans several distinct perturbation logics, and the repair side spans several distinct reinsertion philosophies.

This complementarity matters because no single perturbation-repair pair can cover all failure modes of the incumbent. Random destruction can escape shallow basins but lacks direction, worst removal is targeted but may over-focus on current objective structure, related removal is spatially coherent but may ignore reliability, and low-probability removal is reliability-aware but may ignore combinational cost. Similarly, greedy repair is fast, regret repair protects scarce opportunities, and timeslot-aware repair improves reliability alignment. Taken together, the pool covers the major improvement scenarios visible in the codebase: cost-driven corrections, geographic reorganization, attendance-probability re-timing, and pair-level reassignment.

3.8 SA Acceptance Criterion and Adaptive Weight Updating

Step 1: Simulated annealing acceptance probability.

This step is performed because purely improvement-only acceptance would make the ALNS loop overly brittle once it reaches a moderately good local basin. The SA rule therefore allows occasional worsening moves so that the destroy-repair process can escape local optima.

The acceptance logic first computes the objective difference between the candidate and the current accepted state. Subsequently, strict improvements are accepted deterministically, whereas worsening moves are accepted with the Metropolis probability. Once this rule has been applied, the algorithm can continue to explore without collapsing into monotone hill-climbing.

\begin{equation}
\Delta = Z_{\mathrm{new}}-Z_{\mathrm{cur}}.
\tag{94}
\end{equation}

\begin{equation}
P_{\mathrm{acc}} =
\begin{cases}
1, & \Delta < 0,\\
\exp(-\Delta/T), & \Delta \ge 0.
\end{cases}
\tag{95}
\end{equation}

In Eqs. (61) and (62), \(\Delta\) is the deterioration amount of the candidate relative to the current accepted state, and \(T\) is the current temperature.

Satisfaction is declared when an improving move is encountered or when a worsening move survives the Metropolis draw. A violation occurs when a worsening move fails the draw; in that case, the candidate is rejected and the current accepted state is preserved.

The output of this step is one acceptance or rejection decision for the already pre-screened candidate.

Code location. src/spd/aco_alns.py::ALNSOptimizer.optimize, called by src/spd/aco_alns.py::_run_single_ant.

Step 2: Temperature schedule and numerical behavior.

This step is performed because the acceptance rule in Eq. (62) must evolve from exploratory to exploitative behavior over the ALNS horizon. The implementation therefore uses geometric cooling with a hard-coded numerical lower bound rather than a separate symbolic stopping temperature.

The initial temperature is taken directly from configuration, and the temperature is then multiplied by the cooling rate at every ALNS iteration. Consequently, the SA mechanism cools smoothly but never reaches exact zero. In the reference setting with \(T_0=100\), \(\alpha_{\mathrm{sa}}=0.98\), and \(L_{\mathrm{alns}}=50\), the temperature after fifty updates is: 

\begin{equation}
T_{50}=100\times 0.98^{50}\approx 36.4170.
\tag{96}
\end{equation}

\begin{equation}
P_{\mathrm{acc}}(\Delta=1 \mid T=T_{50})
=
\exp(-1/36.4170)
\approx 0.9729.
\tag{97}
\end{equation}

In Eq. (63), \(T_{50}\) is the temperature after fifty geometric cooling operations. In Eq. (64), the acceptance probability is evaluated for a unit worsening move. This numerical result shows that the configured cooling schedule is still relatively permissive after 50 inner iterations. Consequently, exploitation in the present implementation is shaped not only by temperature cooling but also by the finite ALNS budget, the reward-driven operator bias, the pre-check, the best-feasible gate, and the finite ACO outer budget of 20 iterations. The total search budget therefore remains exploratory at the inner-loop level but is still bounded globally by only 20 outer iterations times 5 ants in the reference configuration.

Satisfaction is declared when temperature remains positive and updates monotonically downward. A violation occurs only numerically if temperature would underflow; in that case, the implementation clamps it at \(10^{-9}\). The output of this step is one cooled temperature value for the next ALNS iteration.

Code location. src/spd/aco_alns.py::ALNSOptimizer.optimize. Configuration variables are params.alns.sa_initial_temperature and params.alns.sa_cooling_rate. No separate T_min parameter was found; the lower bound is the hard-coded constant 1e-9.

Step 3: Reward classes and adaptive operator-weight update.

This step is performed because the destroy and repair operators play different roles over the search trajectory and their future selection probabilities should respond to observed usefulness. The implementation therefore maps each accepted or rejected outcome into one reward class and updates only the selected destroy and repair weights.

The reward classes are \(\sigma_1\) for a new global best, \(\sigma_2\) for an accepted improvement that is not globally best, \(\sigma_3\) for an accepted worsening move, and zero for rejection or invalidity. Once the reward has been determined, the selected weights are updated by exponential smoothing with reaction factor \(r\). In the reference setting, \(\sigma_1=33\), \(\sigma_2=13\), \(\sigma_3=9\), and \(r=0.1\). Starting from \(w^{(0)}=1\), repeated \(\sigma_1\) rewards produce 

\begin{equation}
w^{(k+1)}=(1-r)w^{(k)} + r\sigma_1.
\tag{98}
\end{equation}

\begin{equation}
w^{(k)} = \sigma_1 - (\sigma_1-w^{(0)})(1-r)^k.
\tag{99}
\end{equation}

Under \(w^{(0)}=1\), \(\sigma_1=33\), and \(r=0.1\), one obtains \(w^{(1)}=4.2\), \(w^{(5)}\approx 14.1037\), \(w^{(10)}\approx 21.8426\), and \(w^{(20)}\approx 29.1086\). This growth pattern shows that a moderately small reaction factor preserves diversity for several iterations while still allowing clearly superior operators to dominate gradually. If \(r\) were too large, operator diversity would collapse rapidly after a short reward streak; if \(r\) were too small, the adaptive mechanism would become too inert to exploit meaningful operator differences within the available search budget.

Satisfaction is declared when the selected operator pair receives a reward consistent with the realized search outcome and the updated weights remain numerically stable. A violation occurs when the candidate is invalid or rejected; in that case, the same update law is applied with zero reward, thereby penalizing the selected operators. The output of this step is an updated destroy-repair weight state that will shape the next roulette selection. Code location: src/spd/aco_alns.py::ALNSOptimizer.optimize. No segment-based update was found; the implementation updates weights once per ALNS iteration.

The mutual interaction among the destroy and repair families becomes clearer when the full adaptive system is considered. D1, D2, D3, and D4 do not simply compete; rather, they represent orthogonal disturbance principles, and the weight update allows the search to bias toward whichever disturbance mode currently aligns with improvement opportunities. In turn, R1, R2, and R3 do not merely rebuild the destroyed solution in different styles; they define three distinct priorities, namely immediate objective reduction, preservation of fragile insertion opportunities, and alignment with high-probability arrival slots.

The overall design therefore covers several major search scenarios. When the incumbent suffers from obvious high-cost local structure, D2 and R1 or R2 can become dominant. When the incumbent is geographically tangled, D3 paired with R2 can restructure the neighborhood more effectively. When the incumbent is reliability-exposed under the slot probability model, D4 and R3 provide a targeted combination. Consequently, the adaptive scheme is not merely a probabilistic scheduler; it is the mechanism that lets the search move among several complementary structural diagnoses.

3.9 Stopping Conditions, Complexity, and Parallelization

Step 1: Outer and inner stopping conditions.

This step is performed because the nested algorithm requires explicit termination at both the ACO and ALNS layers. Without separate stopping rules, the outer search would have no global budget control and the inner local search would have no bounded computational horizon.

The ALNS inner loop stops after a fixed number of iterations params.alns.iterations. The ACO outer loop stops either when params.aco.max_iterations has been exhausted or when the no-improvement counter reaches params.aco.no_improve_max. Once the latter condition has been triggered, the solver breaks the outer loop immediately, even if the absolute iteration limit has not yet been reached. Consequently, the no-improvement criterion has priority as an early-stop mechanism inside the global iteration budget.

\begin{equation}
\text{stop}_{\mathrm{ALNS}} \iff t_{\mathrm{alns}} = N_{\mathrm{alns}}.
\tag{100}
\end{equation}

\begin{equation}
\text{stop}_{\mathrm{ACO}} \iff
\left[t_{\mathrm{aco}}=I_{\max}\right]
\lor
\left[\mathrm{noImprove}\ge N_{\mathrm{noImprove}}\right].
\tag{101}
\end{equation}

In Eqs. (67) and (68), \(N_{\mathrm{alns}}\) is params.alns.iterations, \(I_{\max}\) is params.aco.max_iterations, and \(N_{\mathrm{noImprove}}\) is params.aco.no_improve_max.

Satisfaction is declared when either the fixed budget or the early-stop criterion is reached at the appropriate layer. A violation does not represent infeasibility here; rather, it means that neither stopping condition has yet been reached, in which case the algorithm continues normally. The output of this step is one termination decision at the inner or outer search layer.

Step 2: Complexity decomposition.

This step is performed because the practical cost of the nested optimizer depends on both constructive and local-search layers. A meaningful complexity discussion must therefore separate the ACO budget, the per-ant constructive cost, the ALNS cost, and the pheromone update cost.

Let \(I\) be the number of ACO outer iterations, \(A\) the ant count, \(L\) the ALNS iterations per ant, and \(N\) the customer count. The total budget can be expressed as one outer-loop multiplicative shell around constructive and local search cost, plus pheromone maintenance. The most expensive constructive part arises from repeated candidate evaluation during route growth. The most expensive ALNS parts arise from repeated objective evaluation and feasibility checking, with D2 requiring special attention because it evaluates a single-removal objective for every customer and therefore incurs a quadratic-style marginal-analysis burden relative to simple random removal.

\begin{equation}
\mathcal{T}_{\mathrm{offline}}
\approx
I\cdot A\cdot\left(
\mathcal{T}_{\mathrm{construct}}(N)
+
\mathcal{T}_{\mathrm{ALNS}}(L,N)
\right)
+
I\cdot \mathcal{T}_{\mathrm{pheromone}}.
\tag{102}
\end{equation}

In Eq. (69), \(\mathcal{T}_{\mathrm{construct}}(N)\) includes route extension, candidate expansion, and sortie extraction; \(\mathcal{T}_{\mathrm{ALNS}}(L,N)\) includes destroy-repair, fallback rebuild, pre-check, hard-feasibility gating, and objective evaluation; and \(\mathcal{T}_{\mathrm{pheromone}}\) includes evaporation and edge deposition over the pheromone dictionary.

Satisfaction is declared when the algorithm remains within the available runtime budget for the chosen parameter setting. A violation occurs when one component dominates excessively, as in large instances with expensive D2 marginal scoring or heavy fallback usage; in that case, runtime grows substantially even though the algorithmic logic remains unchanged. The output of this step is a layer-wise understanding of computational burden rather than one exact closed-form complexity bound.

Code location. Step 3: Parallel ant execution and serial fallback.

This step is performed because the ant tasks are naturally independent within one ACO outer iteration until best-solution aggregation and pheromone update are required. Parallelizing at the ant level can therefore reduce wall-clock time without changing optimization logic.

The solver determines whether ant parallelism should be enabled from the optional parallel_ants setting and from the available CPU count. It then chooses at most min(ant_count, cpu_count-1) workers and launches a multiprocessing pool with spawn semantics. Once one outer iteration has been completed, the results are synchronized, the best refined ant is identified, and pheromone update is performed serially. If pool creation or parallel execution fails, the implementation falls back to serial execution for robustness. Consequently, parallelization changes runtime but not search semantics.

\begin{equation}
n_{\mathrm{workers}} =
\min(A,\max(1,\mathrm{CPU}-1)).
\tag{103}
\end{equation}

In Eq. (70), \(A\) is the ant count. Parallel execution is used only when \(A>1\) and at least two workers are available.

Satisfaction is declared when the worker pool is created successfully and ant tasks return results normally. A violation occurs when multiprocessing setup or execution fails; in that case, the implementation logs a warning and re-executes the same outer iteration serially. The output of this step is either one parallel ant-result set or one serially computed ant-result set with identical logical meaning.

3.11 Pseudocode in Algorithm2e Format

This operation is performed because the complete optimizer is easiest to understand as a two-layer control flow before line-by-line pseudocode is read. The input semantics are the problem instance, the parameter bundle, and a random generator; the output semantics are one best feasible offline solution. The design logic is that ACO allocates global search budget across ants and outer iterations, whereas ALNS improves each ant locally before pheromone learning occurs. Once these two roles are separated, the full algorithm becomes structurally transparent.

\begin{algorithm}[H]

  advance\_beta\_schedule(...)\;

\end{algorithm}

This operation is performed because the pheromone updater is the point where current-iteration evidence and incumbent memory are fused, and that role should be stated before the pseudocode is read. \begin{algorithm}[H]
\caption{Pheromone Evaporation and Dual Deposition}

Algorithm 4: ALNS inner loop with full feasibility hierarchy.

This operation is performed because the ALNS inner loop is the algorithmic core of local improvement, and its layered logic should be stated explicitly before the pseudocode is read. Its input semantics are an ant-constructed initial solution, the parameter bundle, and the global-best reference objective; its output semantics are one hard-feasible local best. The design logic is hierarchical: destroy and repair generate candidates, fallback rebuild restores damaged structure, the pre-check filters physically impossible states, SA controls acceptance, and full hard-feasibility gates the returned best.

\begin{algorithm}[H]
\caption{ALNS Inner Loop}
\KwIn{initial solution, params, home\_status, global-best objective}
\KwOut{best\_local feasible solution}
initialize current solution, best\_local, temperature, operator weights\;
\For{$it=1$ \KwTo $N_{\mathrm{alns}}$}{
  select destroy and repair operators by roulette\;
  sample removal count\;
  partial $\leftarrow$ destroy(current)\;
  candidate $\leftarrow$ repair(partial)\;
  \If{candidate has unserved or damaged sortie structure}{
    fallback\_rebuild(candidate)\;
  }
  \If{cross-group trigger fires}{
    candidate $\leftarrow$ random cross-group perturbation\;
  }
  \If{structural-and-physical pre-check fails}{
    assign zero reward, cool temperature, record history, continue\;
  }
  compute candidate objective\;
  apply SA acceptance rule\;
  \If{accepted}{
    update current solution\;
    \If{candidate is fully hard-feasible and better than best\_local}{
      update best\_local\;
    }
  }
  update selected operator weights and cool temperature\;
  record history\;
}
\Return best\_local\;
\end{algorithm}
\tag{107}

The most important lines are the fallback branch, the pre-check branch, and the hard-feasible best gate, because those three lines encode the three-layer feasibility hierarchy of the implementation. Without them, the pseudocode would incorrectly suggest that one single feasibility oracle governs the whole ALNS loop.

Chapter 4 Online Execution

The online execution phase receives the optimized offline solution from Chapter 3 and executes it in a stochastic real-world environment. Unlike the offline phase, which optimizes expected costs under uncertainty, this phase responds to revealed customer availability states in real time. Once not-home events are detected, local replanning and freeze-aware optimization are triggered on the affected execution suffix.

4.1 Online Execution Stage Overview

First, the online stage is positioned as the execution layer that receives an already optimized offline structural solution, where the offline layer provides the truck route sequence, sortie list, pair assignment state, and expected-cost calibration coefficients, while the online layer receives this structure as planned_solution and executes it under realized customer absence. Subsequently, the online stage no longer optimizes under expectation over all unobserved events; instead, it runs a realized trajectory under sampled binary presence and updates the remaining plan only when a not-home event is observed. Finally, the essential distinction is therefore deterministic expectation optimization offline versus stochastic realized response online.

Subsequently, the main challenge is that customer absence uncertainty enters execution as node-level event revelation, because binary outcomes in home_status are sampled from home_probabilities and then consumed by the event engine. In turn, irrevocability appears because visited truck nodes, started sorties, and sortie prefixes before a failed customer are frozen through frozen_customers, which constrains the feasible neighborhood for replanning. As a result, real-time response must compress search depth, since only a lightweight online ALNS with strict-improvement acceptance and a short fixed iteration budget is allowed during execution.

Consequently, the global logic is an execution-sensing-decision loop over each pair route: the engine advances arc by arc, checks truck-side and drone-side not-home events at reached nodes, dispatches event objects, repairs affected sorties, freezes executed decisions, and performs local remaining-path optimization on the affected pair. Once each repair has been completed, timeline and load states are recomputed so that subsequent sortie feasibility is validated before continuing traversal. Thereafter, actual cost is accumulated from realized truck distance, realized drone energy, and realized failure penalties.

Finally, this chapter is organized so that Section 4.2 formalizes online initialization from offline outputs, Section 4.3 details the execution loop and node-level service actions, Section 4.4 explains failure processing and local replanning decisions, Section 4.5 clarifies online feasibility-preservation mechanisms, Section 4.6 summarizes realized-cost reporting structures, Section 4.7 discusses budget-complexity implications of online optimization compression, and Section 4.8 provides a consolidated implementation-level interpretation of the complete online stage.

4.3 Online Execution Main Loop

4.3.1 Main-loop structure overview

The implemented loop is primarily node-arrival-driven over each pair route index rather than globally time-stepped. First, the engine advances from one truck arc to the next, records traveled distance, and then performs node-local event checks. Subsequently, if a not-home event is detected, event dispatch is immediately executed and the current solution is replaced by the returned replanned solution before the loop continues; as a result, loop progression and decision updates are tightly interleaved.

Loop termination occurs when the route cursor reaches the last node of the current pair route, after which the engine moves to the next pair identifier. Once all pair routes have been completed, timelines are recomputed for realized reporting, realized costs are aggregated, and execution output is returned. Consequently, the stopping condition is structural exhaustion of all route positions, and the loop-internal decision sequence is travel update, truck-event check, drone-event scan at launch node, optional replanning, and continuation.

4.4.3 Online re-optimization algorithm

Step 1: Selection of lightweight online optimizer and budget compression analysis.

This step is performed because rerunning full offline ACO-ALNS at each online event would violate real-time response requirements. 4.5 Online Feasibility-Preservation Mechanisms

Step 1: Online maintenance of temporal constraints.

This step is performed because realized service outcomes alter departure times and can cascade into downstream lateness if timeline propagation is not recomputed. Once each relevant event mutation has been applied, truck and drone timelines are recomputed and checked against customer latest bounds through hard-feasibility gates.

Subsequently, temporal infeasibility is handled by candidate rejection in online ALNS and by sortie repair attempts in event handlers, rather than by soft acceptance. As a result, online mode enforces strict temporal feasibility on accepted updates while still allowing internal attempted candidates to be filtered out. 

\begin{equation}
\forall i\in\mathcal{N}_T:\;AT_T(i)\le l_i,
\qquad
\forall j\in\mathcal{N}_D:\;AT_D(j)\le l_j.
\tag{131}
\end{equation}

In Eq. (98), truck and drone arrivals correspond to timeline.truck_arrival and timeline.drone_arrival, and l_i is customer.time_window[1]. Cascade handling is operationalized by recomputing timeline and revalidating subsequent sorties after each accepted repair.

Satisfaction is declared when all accepted updates satisfy latest-time bounds for both truck and drone served customers. A violation occurs when any bound is exceeded; in that case, the violating candidate is rejected or the offending sortie is repaired and rechecked.

The output of this step is a temporally feasible online solution trajectory after each accepted mutation.

4.6 Realized Reporting Structures

Once execution terminates, the engine constructs ExecutionResult with realized timeline dictionary, realized home-status map, failed-customer set, truck-distance and drone-energy traces, actual total cost, and replanning snapshots. Subsequently, this object is consumed by Monte Carlo aggregation and reporting utilities, so online execution remains directly analyzable without rerunning event logic.

4.7 Complexity and Budget Implications

The implemented online solver intentionally compresses neighborhood search to fixed small iterations and limited operators, and therefore each event response cost is approximately linear in online iteration count times candidate evaluation cost for one pair. As a result, the design privileges latency stability under repeated events, while leaving deep global restructuring to the offline stage.

4.8 Consolidated Interpretation

The complete online stage is an event-driven local-repair framework that preserves offline structure, reveals realized uncertainty during traversal, and updates only mutable suffixes under strict feasibility and strict-improvement policies. Consequently, the implementation is consistent with a two-layer methodology in which offline expectation planning and online realized execution are explicitly separated yet computationally coupled through shared state representations.

Chapter 4 outputs realized execution records and realized total cost, including timeline realizations, failed-customer events, and event-triggered replanning traces. These outputs are essential for experimental evaluation because they quantify how offline planning quality translates into realized operational performance under uncertainty.

5.3 Algorithmic complexity analysis

5.3.1 Stage-wise complexity

Initial solution construction (ETPRC). Let N be customer count and K be vehicle-pair count. The main costs come from grouping iteration, route insertion trials, sortie subset enumeration, and rescue insertion checks. Time complexity is approximately O(N·K·I_k + N^2 + N·2^m) where I_k is k-means iteration bound and m is sortie-size cap. Space complexity is approximately O(N + K + |A|). Code evidence: src/spd/etprc.py.

Offline optimization (ACO-ALNS). The outer ACO layer is O(I · A · C_ant); one ant construction is approximately O(N^2) with feasibility checks; inner ALNS is O(L · C_op); one operator-evaluation cycle depends on destroy-repair neighborhood generation and is approximately O(N^2) in common settings; pheromone update is O(|A|). Combined form is approximately O(I · A · (N^2 + L·N^2) + I·|A|). Code evidence: src/spd/aco_alns.py.

Online replanning. Failure detection over route traversal is approximately O(N + |S|); trigger checking is event-local O(1) per inspected customer with scan overhead; lightweight online optimization is approximately O(N_on · C_op_on) where C_op_on is restricted destroy-repair evaluation cost. A practical bound is O(N + N_on·N^2) per affected pair. Code evidence: src/spd/simulation.py and src/spd/online.py.

5.3.2 Overall complexity

The end-to-end complexity is dominated by the offline stage, while online stage cost is event-conditional and locally bounded by lightweight iteration budgets. A practical combined estimate is O(C_stage1 + C_stage2 + E·C_stage3), where E is realized event count. The primary runtime bottleneck is the nested offline ACO-ALNS search, especially under larger I, A, and L values.

5.4 Three-stage top-level pseudocode

The pseudocode below abstracts the complete pipeline from instance input to realized execution output. It emphasizes structural handoff between stages and event-driven online recourse.

\begin{algorithm}[H]
\caption{Algorithm 0: Three-Stage Integrated Procedure}
\KwIn{instance $\mathcal{I}$, parameters $\Theta$}
\KwOut{offline optimum $S^{off,*}$, online result $R^{on}$, realized cost $Z^{actual}$}
Phase 1: $S^0 \leftarrow \texttt{ETPRC}(\mathcal{I},\Theta)$\;
Phase 2: $S^{off,*} \leftarrow \texttt{ACO-ALNS}(S^0,\mathcal{I},\Theta)$\;
Initialize execution state from $S^{off,*}$\;
\For{each route traversal event}{
  detect truck/drone failure events\;
  \If{failure event occurs}{
    repair affected sortie and freeze executed decisions\;
    optimize remaining path by lightweight online ALNS\;
  }
}
Aggregate realized timeline, failures, and costs\;
$R^{on}, Z^{actual} \leftarrow \texttt{ExecutionResult}$\;
\Return $S^{off,*}, R^{on}, Z^{actual}$\;
\end{algorithm}

Design-decision note: the first key decision is to separate global deep search (offline) from local recourse (online) to avoid prohibitive real-time computation. The second key decision is to freeze executed prefixes so that operational irreversibility is respected. The third key decision is to keep shared timeline-feasibility kernels across stages, which improves consistency and reduces implementation divergence.
